# 地图区域分类、摄像机修正与地形网格分层

日期：2026-10-29。第19个研究单元，限定区域查询及其与地形查询的结构差别，不代表碰撞系统已完成。只读已有汇编和美版原ROM，独立保存[前三个地图索引的数据证据](semantic-data/map-region-evidence.json)。基线SHA1 c4d93a58f0f82c526dec8a3fdbda170336303689。

## 0894C读取的是屏幕区域分类

当前选择值来自u16[020011D0]&7F，索引0831408C指针表取得地图记录R，再读取u32[R+74]作为区域布局L。没有在此证明整张地图表的合法选择数量，掩码7F不是表长度检查。

输入坐标为24.8定点。先用x>>12、y>>12把坐标化成16像素格，再查两张ROM表：

| 查表 | 通过实际读取验证的范围 | 公式 |
|---|---|---|
| 0831348C | i=0..1904，共1905项 | table[i]=floor(i/15) |
| 08312C8C | i=0..1269，共1270项 | table[i]=floor(i/10) |

因此等价于按240×160像素求列/行。这里16像素格只是换算中间尺度，不意味着最终查询的是碰撞格。

令col、row为结果，shift=u16[L]：

```text
cell = u16[L + 8 + 2*((row << shift) + col)]
classification = cell >> 12
return classification == 0xF ? 0xF0 : classification
```

本函数只使用单元最高4位。低12位在此没有被解释，不把它们直接命名成地形编号、房间编号或屏幕图块编号。

## 两个不同的特殊返回值

全局检查域为x∈[0,00770FFF]、y∈[0,004F5FFF]（十六进制定点），相当于小于30480×20320像素。负坐标或超出此域直接返回0F，不查表。这个范围对应换算表允许的127×127区域坐标域，不代表任意地图都实际有127×127个单元。

布局中高4位F则返回F0；二者不相同：

- F0：083A0返回真，摄像机模式3/4本轮保留原目标中心，只继续1504C显示插值。
- 0F：来自全局坐标越界，083A0返回假；不能自动当作同一种“冻结区”。

0894C没有读取布局头部的实际宽高后再检验col/row。即使坐标通过全局检查，也不能据此证明在某个较小地图内读取合法。调用者依赖实际地图坐标域及有效边界。

布局头的四个u16样本如下，后续数据按width×height导出；shift与宽度为2的幂关系一致。此处只报告地图索引，不给关卡取未经验证的游戏名称。

| 地图索引 | R | L | 头部[shift,mask,width,height] | 单元数 |

| 0 | 08314414 | 0831430C | [4,15,16,8] | 128 |

## 083D4的摄像机边界修正

它先取得中心分类c，再查询横向±120像素、纵向±80像素处的分类n。相容条件是：

```text
u8(c - n + 1) <= 2
```

对普通小分类值，这允许同类及相邻编号；它不是简单的“分类必须相等”，也不是通用碰撞检测。完整公式有8位回绕，不对特殊值直接套普通整数比较。

普通分支从零开始累计修正，左/右不相容时分别加120像素减x对120像素的余数、或减该余数；上/下用80像素作同样处理。EF1E8是有符号余数助手，负输入需保留其符号语义，不能随意用Python的正模代替。

中心分类E跳过普通上下分类探测，直接令outY=240像素-rem(y,160像素)。这里240、160及普通80各有明确指令来源，不能因视口高度160就将240改为160。其具体关卡设计用途待实际场景证据；本轮只赋予“特殊纵向规则”名称。

083D4输出的是修正量；后续摄像机还可能按标志忽略某轴修正、限速或插值。不能把此输出当最终画面位置。详见[摄像机报告](semantic-camera.md)。

## 不同层的数据不能混用

已确认至少三条相关路径：

| 路径 | 数据结构 | 当前直接用途 |
|---|---|---|
| 0894C | 地图记录+74，8B头、u16单元 | 240×160区域的高4位分类 |
| 089C8 | 地图记录+6C，字节网格 | 取单元高/低半字节选择图形/调色板bank并缓存 |
| 0901C/090D4/09190 | RAM地形编号网格及独立属性表 | 16像素格的形状响应、跨格处理 |

089C8使用字节头中的行移位、宽/高，读取单元后把高/低半字节分别用于资源记录选择；它有实际宽高比较。不能据此替0894C补上不存在的宽高检查，也不能把两个表的分类位视为同一种含义。

### 地形查询的第一层证据

0901C等从020017E0读取u16网格行宽，按row=y>>12、col=x>>12计算编号：

```text
tileId = u16[020017E4 + 2*(row*width + col)]
attribute = u16[u32[020011B8] + 2*tileId]
shape = attribute & 0xF
```

这里是RAM中的16×16像素地形格，不是ROM区域布局单元。0901C的shape=0或attribute&8000时走无当前形状响应分支；shape=1采用整格跨越，其他值通过08312BCC一类函数表，以格内低12位坐标计算响应。090D4/09190使用另一响应表08312C0C，方向和最终返回约定需分开研究。

这些函数没有像0894C那样的统一全局坐标检查；也没有在取tileId后验证属性表长度。因此不把它们描述成任意坐标安全的碰撞API。0901C跨格尝试上限及-1返回是局部算法机制，不等于自动修复损坏地图。
