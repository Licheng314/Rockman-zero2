## 1. 基线 ROM 决策（已定案）

**推荐基线：日版《Rockman Zero 2 (Japan)》，次选美版。**

理由：
- 社区知识全部锚定日版：zeroprac 的 asm 直接按 `Rockman Zero 2 (Japan).gba` 组装；
  它文档里所有 ROM/RAM 地址都是日版地址。rmz3 也选了日版（`rmz3.sha1 = ff7a80…`）。
- 用户现有 ROM（`baserom_translated.gba`，SHA1 `47709ecb…`）是美版 A62E 打了汉化的版本，
  不可直接作字节级匹配基线；但其**代码区未被汉化触碰**（见 §3 证据），静态分析结论仍然有效。

已知校验值：

| 版本 | 校验值 | 来源 |
|---|---|---|
| 美版原版 | SHA1 `c4d93a58f0f82c526dec8a3fdbda170336303689` / CRC32 `CE1E37BB` | TASVideos、RHN、no-intro |
| 欧版 | CRC32 `29A14B59` | RetroAchievements |
| 汉化版(现有) | SHA1 `47709ecbab43267dfc7759e2be2825fc0d65aa17` / CRC32 `e7c9f26a` | 本地计算 |
| 日版 | 头部应为 `ROCKMANZERO2`/代码`AZRJ`；SHA1 待用 DAT-o-MATIC 复核 | — |

拿到候选 ROM 后运行 `python tools/verify_baserom.py <文件> --copy` 自动判定+定位汉化改动区。

## 2. 已完成的分析产物

- `analysis/rom_map.md` — 熵分布、LZ77 清单、代码区识别
- `analysis/functions.tsv` — 18559 个 BL 目标函数入口（初始函数表）
- `analysis/lz77_blobs.tsv` — 1840 个 LZ77 压缩块清单
- `tools/analyze_rom.py` / `tools/verify_baserom.py`

关键结论：
- 主代码区 `0x08000000-0x080F0000`（960KB，Thumb 为主）；`0x080000C0` 起是 ARM crt0。
- 后续 0x0810xxxx-0x082Fxxxx 还有约 1MB 稀疏代码/脚本表混排区。
- `0x080F31F0` 有一个 57668B→65536B 的 LZ77 块：极可能是汉化组的中文字库（原版此处内容待 diff 确认）。
- `0x083D0000-0x08410000` 高熵区 = 大宗压缩图形/音频；`0x084E0000-0x08540000` 低熵区 = 表/文本。
- zeroprac（日版）记载 `0x0835780C-0x0836DAF0` 为空洞区、`0x08360000` 有 "PLATINUM"（疑似 debug）。

## 3. 汉化版代码区可信的证据

gpSP 模拟器官方配置为**干净美版**标注的 idle loop 地址是 `0x08000664`；
本汉化版该地址恰好是 `blo 0x08000652`（构成回跳循环的指令）——
若代码区被改，此处几乎不可能恰好保持。待干净 ROM 到位后用 verify_baserom.py 全量复核。

## 4. 现成知识（转载自 zeroprac，均为日版地址，注意换算）

RAM（EWRAM）：
- `0x02000D10` 按键（半字，低有效）；`0x0202EC34` 按键（高有效）
- `0x0202E188` RNG；`0x0202EBB4` 游戏进度；`0x0202EBF8` 关卡时间
- `0x0202EC30` 关卡索引；`0x0202EC32` 检查点；`0x0202EC38` 演出可跳过标志
- `0x0202EC40..4C` 脚本基址/关卡脚本；`0x0202EC60` Boss 指针；`0x0202EDAC` 关卡状态
- `0x0202F8E1` 游戏状态机：0=intro 1=读档 3=进关卡 4=游玩 5/6=暂停 7=退关 8=game over
  **9=debug 选关菜单**（原版隐藏功能！）A/B=片尾
- `0x02037CF0` Zero 结构体基址（`+0xA4` 当前血量, `+0x17E` 重生血量, `+0x206` 副水箱1…）
- 关卡数据装在 EWRAM `0x0017E4-0x02D004`；BG0/BG1 在 EWRAM，BG2/BG3 从 ROM 拉取
- IWRAM `0x03000000` 起有一段 ARM 代码（`0x30015C8-16DC` 又一段）——引擎热路径

ROM（日版）函数锚点：
- `0x08013448` 取敌人构造函数；`0x0803703E` 武器检查
- `0x080DF850/080DFA12` 文本框输入；`0x080E4044` 游戏状态检查；`0x080E43FD` 开始关卡；
  `0x080E5331` 选关菜单；`0x080EF1B4` BIOS 函数封装
- `0x08333A00/10` 按键方案 A/B 数据
- `ROMADDR_STORE_ZERO_DATA=0x08031198`、`SET_ZERO_ENTITY_MAX=0x080E44DA`

## 5. rmz3 工程结构（rmz2 的模板）

- pret 式：`src/*.c`（71 个文件已反编译, 函数上方注释原地址如 `// 0x0801a5bc`）+
  `include/` 头文件 + `linker/{ewram,iwram,rodata,text}.txt` 段放置文件
- 构建链：**agbcc**（唯一可用, "modern" 构建因硬编码地址失效）+ GNU make + **Deno**（构建脚本）+
  pret 移植工具（`tools/`: gbagfx, mid2agb, preproc, scaninc, dumper, dev）
- 资产已提取：`sprites/` 14M、`sound/` 3.7M、`data/` 3.1M、`graphics/` 839K
- 引擎模块划分（rmz2 应沿用）：animation/camera/collision/entity_manager/enemy/boss/
  cyberelf/physics/stage/weapon/widget/game/libs
- 音乐驱动 = m4a（根目录 `MPlayDef.s`）
- asmdiff.sh：逐函数与原 ROM 字节 diff 的匹配循环

## 6. rmz2 落地步骤（拿到干净 ROM 后）

1. `python tools/verify_baserom.py <rom> --copy` → 得到 `baserom.gba`（日版优先）
2. 用 functions.tsv 建 Ghidra/自研标注底账；日版地址需重定位（zeroprac 锚点函数可互校）
3. 仿 rmz3 搭 Makefile/ld_script/extract 工具（Deno→可先用 Python 复刻）
4. WSL 装 agbcc（D 盘紧张, 工具都放 C 盘）
5. m2c + asmdiff 逐函数反编译；先啃 crt0 → 主循环 → 游戏状态机(0x0202F8E1 驱动) → 实体系统
6. 数据侧：LZ77 块逐个鉴定（字库/图形/关卡），产出 extract/repack 工具

## 11. 2026-10-25 第五轮: C 字节匹配闭环上线

  objcopy → 与ROM逐字节diff, 输出首差异位置+匹配率。

## 12. 匹配迭代记录 (Entity_SetScript)

- 全量差异图谱(analysis对齐): 生成81条 vs 原始88条, 差7条 ≈ 6×"mov rX,ip"重载+1条派生。
  序言外的指令序列基本一致(寄存器号也对得上)。
- 根因: 原版分配 {ip:e, r5:arg1, r2:id(跨块), r4:sub, r3:t3}; agbcc 给我们的是
  {r3:e(活到bl前最后使用), r6:arg1, ...} — e 不进 ip 导致链式多压 r6。
- 尾部是普通 bl + interwork 返回(pop {r4,r5}; pop {r0}; bx r0), 不是尾调用。
- 已试: 表达式形状矩阵(u16/int参数、m2c逐句、显式!=0)、-O1/-O2/-fno-expensive、
  提前子指针/额外字节指针 → 序言均不变(12.9%)。
- 研究了 rmz3 已验证源码的 ip 用法(编译40个文件): rmz3 中 mov ip 多为字面基址/比较scratch,
  未见参数保存型序言 — Z2 的该习惯用法可能需要特定源形状或实际 gcc2.95.2 与 agbcc 重建的差异。
- 下一步思路: ①在 rmz3 编译产物中找"push后紧跟 mov ip,r0"的函数并对照其 C 源;
  ②或先批量做 asm 级提取(零风险推进), C 匹配作为长期线。
