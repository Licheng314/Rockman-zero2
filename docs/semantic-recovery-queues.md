# 恢复计时队列与储量转存

2026-10-29 只读语义轮。未停止后台，未改变源码、构建清单或工具。结论来自原ROM常量/指令以及已有汇编；静态分析尚未做游戏运行取证。

## 与储量模块的连接

sub_08022FEC 是统一的恢复一步操作，0x0802302C是其中的内部块，不是独立函数。最初按目标地址找同名文件会漏掉这类情况；tools/segments.json中的start/end是ROM偏移，比较虚拟地址时必须先减0x08000000。

其操作如下，名称只为说明用途：

```text
current = signed16(entity+0xA4)
limit = unsigned8(sub_08022AF0(entity))
if current < limit:
    step = unsigned8(sub_08022B0C(entity))
    current = min(current + step, limit)
    store16(entity+0xA4, current)
    sub_0801E6AC(0x1F)
    return current < limit
else:
    callback = ROM32(0x08333B9C + entity[9]*4)
    return unsigned8(callback(entity))
```

22AF0表基址0x08333B58；22B0C表基址0x08333B5C。就索引0而言，分别调用37A3C（上限）与37A5C（常数1）。第三个表基址0x08333B9C的索引0为389D0（储量补充）。三个索引合法域仍未确认；不将相邻表项认定为多个角色实现。

重要边界：当前值不足时最后一步恰好加满会返回0，并不在同一次调用继续存储盈余；要有之后的新一次调用才会走储量补充。当前值已经超过上限时直接调用储量回调，不先钳回上限。step为0且当前值不足时返回1，无法单靠返回值保证数值有进展。

## 全局计数器及调度者

sub_080E5AF4从传入上下文+0x75B8读取实体指针，按以下顺序处理：

| 全局地址 | 本轮确认的行为 | 暂定名称 |
|---|---|---|
| 0x0202E150 | 每次减1，低2位为3时调用2306C(entity,4)，实际增加量为0则清计数器 | 另一资源补充计时器，类型未定 |
| 0x0202E180 | 当前值未满时保留；满值时整体转入E18C；后续每4次调用执行一次22FEC | 当前值优先的恢复计时器 |
| 0x0202E18C | 可接收E180转入值；每4次调用执行一次22FEC | 满值后的储量补充计时器 |
| 0x0202EC30+8 bit0x10 | 置位时跳过E18C处理，并清E180 | 恢复抑制标志，游戏状态名称未定 |

调度精确次序：

1. E150非0时减1，新值满足 `(value & 3)==3` 才调用2306C；实际增加量0时清E150。
2. 读取抑制标志。若置位，清E180并返回；E150已在此前处理，E18C保留而非清零。
3. 若E180非0且当前值已满，E18C += E180，E180=0。累加未见显式饱和保护，按机器字宽算术，不假定不溢出。
4. 对E18C：非0则减1，相位为3时调用22FEC；返回0则清此计数器。
5. 对E180重复同样的倒计时与22FEC规则。

这里“每4次”以E5AF4的调用次数计，不直接宣称每4帧，帧调度入口尚未确认。若两个计数器同时活动，单次E5AF4可能分别执行两次22FEC，不应合并为共享一个节拍。

## 返回值协议及来源

389D0在加1后仍未满时返回1，在刚加满时返回0。22FEC将这个结果传到E5AF4，所以0表示此次恢复操作不要求继续，不能简单等同于失败或未发生写入。把它误改为“只要补充成功就返回1”将改变队列清空时机。

sub_08039FF4处理某种接触/效果路径：在其条件成立后，若全局0x0202E140的字节非0，直接调用22FEC；否则给E180加4。其它路径尚涉及3A130、实体+0xB4等关联数据，故暂不正式命名为某具体拾取物。加4与每4调用执行一次相吻合：从计数4开始，第一次减到3即触发一次，之后2/1/0不触发；恰好提供一次恢复机会。

sub_080D4B4C内有给E180加0x10、0x20、0x100的路径；全局0x0202EBB0+0xB的bit0x80会在这些路径额外加同样的量。另有加到E150的4/0x10路径。足以识别为资源补充效果系列，但尚不能给具体效果ID起最终游戏名字。

23214是对22FEC的低8位返回值包装。2304C/2306C是另一资源的饱和增加，使用22A54返回的16位指针和另一上限表，不能与entity+0xA4生命恢复机制合并。

## 下一步与未验证项

- E5AF4的上层调度，确定是帧更新还是其他节拍。
- 0202E140及0202EC30 bit0x10的写入者，确定即时/限速和抑制模式。
- entity+0xA4的扣减路径，继续互证生命值解释。
- 389D0在新槽恰好满值后返回0导致剩余计时清除是原行为，保留；是否有外部队列再次补充下一槽需追踪。
- 本文伪代码只是语义说明，不是已验证C集成；正式C数量不变。

## 状态门控补充

本报告“每4次调用”的适用范围由[状态门控报告](semantic-runtime-gates.md)补齐：二级状态4才选择E4390更新；E4390存在早退，也存在跳过对象更新但继续恢复的路径。EC30+8 bit0x10的一个来源是14DE8发现实体当前值0或状态bit0x200；该来源同时清bit0。E140影响多子系统，暂不命名为单纯即时回血开关。
