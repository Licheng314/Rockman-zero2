# 按键采样、边沿与逐键连发

日期：2026-10-29。第16个研究单元，只读已有汇编与美版原ROM，独立保存研究。基线SHA1 c4d93a58f0f82c526dec8a3fdbda170336303689。[结构与静态时序证据](semantic-data/input-state-evidence.json)。

本轮区分采样计数和游戏帧，不改变按键处理、后台提取或正式构建。

## 两个24B输入记录

01FC4依次调用01FE4(record,index)，index=0/1，记录基址02000D10/02000D28，步长18（十六进制，即24字节）。这只证明两个输入通道，尚不把它们等同于两个玩家实体。

| 记录偏移（十六进制） | 大小 | 已证实用途 |
|---|---|---|
| +0 | u16 | 当前按住位图：从选定源读取u16后取反再截16位 |
| +2 | u16 | 上次按住位图；每次先从旧+0复制 |
| +4 | u16 | 新按下边沿：(current XOR previous) AND current |
| +6 | u16 | 本次连发事件位图，正常采样每次清零重建 |
| +8 | u16 | 输入源状态：0未采样、1本地/选中通道、2其他传输通道 |
| +A..+13 | 10×u8 | 每个按钮各自的连发倒计时 |
| +14 | u8 | 首次按下后的等待参数，默认24 |
| +15 | u8 | 后续重复间隔参数，默认4 |
| +16..+17 | 2B | 本轮未定 |

按钮位按[libgba输入定义](https://github.com/devkitPro/libgba/blob/master/include/gba_input.h)核实：01 A、02 B、04 Select、08 Start、10 Right、20 Left、40 Up、80 Down、100 R、200 L（数值均十六进制）。本游戏没有调用该库的keysDown函数，本报告只借其硬件位定义互证按钮名；不能套用该库“读取后清除”接口语义。本游戏的+4/+6是内存字段，读取本身不清除。

01FE4存储取反后的低16位，没有再AND 03FF；其连发循环只遍历bit0..9。因此不要把完整current字段自动归一化成仅10位，也不对保留高位赋玩家操作含义。

## 本地硬件与传输源

01FE4检查另一结构02000CA0的+2掩码04。清除时：通道0从04000130读取，状态设1；通道1状态设0并提前返回。置位时：从02000CA0+24+2*index取输入u16，若02000CA0[4]==index则状态1，否则状态2。

通道1提前返回之前已把旧current复制到previous，但没有清current、pressed、repeat或逐键倒计时。因此状态0不等于所有输入字段已归零；切换模式的调用者必须尊重状态或执行初始化，不能只读旧pressed字段判断新事件。本轮未对所有传输模式做完整状态机证明。

0132C主要处理02000CA0的传输/中断相关状态，并不是本文的两个按键记录。020D0使用02000D40的状态和083123A4表进行另一套分派；不要因它们在显示任务里相邻调用，就认为020D0是01FE4的同义包装。

## 连发的精确边界

对每个bit0..9，正常采样逻辑：

```text
if not held:
    countdown = 0
else:
    if countdown == 0:
        repeat |= bit
        countdown = initialDelay if pressed else repeatInterval
    countdown = (countdown - 1) & 255
```

因此repeat包含首次按下，但pressed只有上升沿，持续按住不会重新出现在pressed。十个计时器彼此独立，多键同时按住各自计数，不能建模成一个全局连发计时器。

01F98先对两记录调用020A0清当前/旧值/边沿/连发/状态及10个倒计时，再设initialDelay=24、repeatInterval=4。0051C也显式写这两组默认参数；E1114的初始化路径调用01F98。020A0自身不修改参数字节+14/+15。

默认值下，从清零状态连续按住同一个键，采样编号为1,2,...：

| 采样 | 新按下+4 | 连发+6 | 本键剩余倒计时 |
|---|---|---|---|
| 1 | 有 | 有 | 23 |
| 2..23 | 无 | 无 | 22..1 |
| 24 | 无 | 无 | 0 |
| 25 | 无 | 有 | 3 |
| 26..28 | 无 | 无 | 2..0 |
| 29、33… | 无 | 有 | 3 |

释放会清该键计时器；随后重新按下立即有pressed与repeat。等待24的含义是第一次事件与下一次相差24次采样，不是“第24次采样就连发”。默认4同理是事件间距。参数0也没有特殊禁用逻辑，装0后立即减为FF，后续会等字节绕回；不能把0解释成即时重复或关闭连发。

代码没有硬件防抖窗口或强制剔除相反方向键：同一次采样的多个位可共同保留。后续菜单分支各自决定优先级，不能从采样器假设只有一个方向有效。

## 菜单为什么有的长按有效、有的没有

| 消费者 | 使用字段 | 已确认行为 |
|---|---|---|
| D5C94类别选择 | +4与C0 | 新按Up/Down调整类别，钳在0..2；该函数本身不接收连发 |
| D5DD4网格方向入口 | +4与F0 | 新按方向再分派纵向/横向处理 |
| E9050储量槽选择 | +4 | A确认、B返回、Left/Right换非空槽；该函数无连发字段读取 |
| E8510关闭判定 | +4与08 | 只看新按Start |
| EC384成长金额编辑 | +4、+0、+6 | B取消/A确认/左右换数位使用边沿；上下金额变化使用按住与连发 |

“本函数不接收连发”不排除别处主动改变选择；它限定所读调用链，不能外推全游戏长按失效。

EC384先看current的C0确认方向仍按住，再看repeat的C0决定本次是否增减10^digit，最后钳到0..maxSelectable。到边界时另外读取pressed：在最大值新按Up可绕回0，在0新按Down可跳最大值；单纯按住到边界的重复事件不会反复绕回。这解释了同一编辑器同时使用三个字段的原因。

按住Up且金额中间值时每次repeat递增；抵达最大值后继续按住保持最大值。释放再按Up才触发边界回零。这些是正常数字域下的指令推导，未做模拟器交互验证；同时按相反方向时仍须按具体分支判优先级，不套单键示例。

## 调度与时间单位

005FC显示任务在调用0132C及状态检查之后，于08000788调用01FC4，随后执行字形/调色板/OAM等提交。该位置位于扫描线和计数字节轮询之后，为按键周期与显示节奏的连接证据。

但采样函数也有01F88初始化后立即采样等调用，任务可能受模式和调度影响；24/4只称采样次数，不换算成毫秒或保证所有模式每帧一次。菜单读取的是最近一次已保存状态，不直接读取硬件寄存器。
