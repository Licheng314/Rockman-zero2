# 阶段 2C：攻击模组接入条件（剑与普通枪弹）

2026-11-08，Codex。用户授权继续推进后，在独立检查副本进行不依赖 2A/2B 验收的前置研究。**首批解释普通剑的基本关联/退场；第二批补普通枪弹的登记、清理与图形槽元数据；第三批补调色板请求、共享与实际发布；第四批补所选普通剑图块刷新入口。累计 15/15 个新增深入函数，达到本阶段深研上限，阶段 2C 仍未完成，不实施改版。** 输入缓冲与连招修补由 ZCode 负责，本批不重复调查。

基线是美版原 ROM，SHA1 `c4d93a58f0f82c526dec8a3fdbda170336303689`。样本来自阶段 1 的普通难度序章状态，使用 RAM 把已有剑放在主武器槽；没有解锁新武器、改成长、保护计数或磁盘存档。普通首斩按一次攻击后放开；其余夹具另行列明。

## 身份、创建与关联

本样本身份固定为池句柄格 `0x0202F070`、类型表 `0x08336060`、类型字节 **3**。表项指向生命周期表 `0x08336564`，五个回调（清除 Thumb bit 后）依次为 `3A288 / 3A408 / 3A79C / 39088 / 06C28`，均为 `0x08000000` 地址空间。不能将其他池的类型 3 当成同一对象。

创建器 ABI 的静态读法为：`r0=所有者`，`r1/r2/r3` 写对象 `+0x10/+0x11/+0x12`；第五个参数写 `+0x13`，第六个参数交给 `0x08037DEC`，第七个参数写 `+0x66`。这些是原始参数位置，未证明每个参数都可任意组合或具有相同单位。

创建器从该池通过 `0x08006B50` 分配，成功后设置类型、初始回调、图形槽相关字段，写：

```text
weapon.owner(+0x28) = zero
zero.current_link(+0x2C) = weapon
return weapon
```

返回 NULL 的分支不写这些关联。运行中把武器池空闲链头暂设为 NULL，观察不到类型 3 生成，所有者指针和空闲数保持原值；这是**分配返回空的 RAM 夹具**，不是自然填满对象池的容量测试。池头、计数及链表的实际容量压力仍待验证。

## 保活与退场合同

`0x0803A994(weapon, owner)` 的原版条件是：

```text
允许继续 = owner[+0x0D] <= 4
           且 owner[+0x2B6] == 1
           且 owner[+0x2C] == weapon
```

三者有一项不满足就返回 1，更新函数转入 `0x0803A79C`。`+0x2B6` 在本样本充当门控，尚未验证它在全部动作中的完整角色，不把它笼统命名为“攻击开关”。这是读取合法 owner 指针之后的状态检查，不是空指针或悬空指针保护；不能传入任意地址期待安全返回。

验证使用一个原版剑对象，把其 owner 指向 RAM 中的角色结构副本，避免给真实 Zero 设置非法动作导致上层分派异常。保持关联正确时，副本 `phase=0, gate=1` 的对照仍为状态 1；只把 gate 改为 0，或只把 phase 改为 5，均在下一次对象更新进入状态 4。此结果验证所选输入，不声称自然游戏可进入这些人工状态。夹具暂存地址 `0x0203F400` 只服务本次可恢复快照，未证明可作为实际模组的永久空闲 RAM。

退场函数的顺序：

1. 把对象 `+0x0C` 整字设为 4，并把 `+0x14` 回调改为该类型表的退出项（本样本为 `0x08006C29`，含 Thumb bit）。
2. 清对象 `+0x8C/+0x90` 两个字与 `+0x94` 字节；清 `+0x0A` 的 bit 2 和 bit 0。
3. **只有** `owner[+0x2C]` 仍等于自己时才将其清零，不覆盖已经替换的新值。
4. 返回；真正归还池由后续更新调用 `0x08006C28` 完成，不是立即释放。

原版普通首斩样本从首次按攻击计：第 **19 次更新**进入状态 4，关联清零但仍在活动链；第 **20 次更新**才从活动链消失，空闲计数加 1。不是普适的“所有剑技持续 19 帧”。另一个 RAM 夹具把 Zero 的关联改成占位新值，旧剑在下一次更新退场并保留该值，再下一次更新归还池。占位值仅用于相等比较，没有把它作为新攻击对象运行。

因此，复用该原版剑处理器时必须同时满足所有者门控与关联协议，接管和销毁要避免旧对象清掉新对象。回收接口还依赖当前池上下文，不能把 `0x08006C28` 当作脱离调度环境的任意 free。

## 动画、碰撞与参数边界

初始化按对象 `+0x10` 从 `0x083375BC` 选择子处理；更新按同字段从 `0x083375D4` 选择子处理。更新仅在实体仍为状态 1 时继续跟随所有者坐标、调整朝向并推进动画。两个索引表的全部合法子型及其范围尚未列齐，不为新模组分配任意子型号。

更新前后比较 `+0x68` 和有符号 `+0x71` 两个索引，发生变化时经 `0x0803AA00` 更新描述符。它从 `0x08337584` 开始做双层指针索引；参数计算包含：

```text
amount = max(1, u8[0x08335AA6 + weapon[+0x13]]
                + s8[weapon+0x67] + u8[weapon+0x66])
```

随后把 body、选中描述符及 amount、0、`s16[weapon+0x64]`、`u8[weapon+0x66]` 交给共享 `0x08006E18`。这里保留原始类型和参数，不把这些值直接等同于敌人的实际 HP 损失；最终命中与连击仍待 2B 解释。

本批普通首斩观测到描述符 `0x08336594 → 0x083365F4 → 0x08336624 → 0`，可见“剑实体存在”和“当前有攻击描述符”不是同一条件。没有重新测量各描述符对敌人的伤害，没有据序列命名三连斩的三次按键。

第二批仍在同一原版序章基线，不涉及新招式、输入缓冲或连击平衡。新增 5 个深入函数：

| 函数 | 本批解释 | 证据层级 |
| --- | --- | --- |
| `0x080391B0` | 复用或创建类型 0 伴随对象 | 静态及关联存在/缺失、分配失败对照 |
| `0x08039470` | 普通弹更新入口、清理请求与所选格挡分支 | 静态及原版运行/显式状态夹具 |
| `0x080396AC` | 清命中状态、进入退出回调并解除登记 | 静态及正常/请求退场对照 |
| `0x08035878` | 四登记槽逆序查找与计数递减 | 静态及登记一致性反例 |
| `0x08037DC8` | 根据角色字段选择资源元数据槽 | 静态及槽 0/1 运行对照 |

创建器 `0x080396EC`、初始化 `0x0803927C` 复用阶段 2；本批补充创建/清理接口解释，不增加新的深研预算。类型 0 的完整生命周期、类型 1 的全部子状态、命中回调及资源传输函数未展开。证据见[第二批记录](semantic-data/stage2c/buster-second-batch-20261108.json)，12 组条件均运行原版，特殊条件只写模拟器 RAM。

### 三种不能混为一谈的容量

- 所选运行中的武器池容量为 **24 个**，对象步长 **236 字节（0xEC）**；剑、枪弹和伴随对象共用此池。不是可供新模组独占的 24 发子弹预算。
- 所有者 `+0x290/+0x294/+0x298/+0x29C` 是本链的 **4 个登记槽**，`+0x2BA` 是 u8 登记计数。4 个槽不等于正常输入必然能同屏发 4 弹；上层发射门仍由 2B 研究，不在本批改写或外推。
- 图形槽选择是另一层状态，不能由对象池空闲数推断 VRAM 或调色板有足够容量。

`0x080396EC` 先通过 `0x080391B0` 取得所有者 `+0x28C` 指向的类型 0 伴随对象；存在时复用，不存在时尝试从同一池分配并建立 owner 关联。取得成功后才另分配类型 1 枪弹。因而缺少伴随对象时，一次发射可能需要两次池分配；已有非零指针只作为复用条件，不是完整有效性验证。

本样本发射前伴随对象已存在，枪弹消失 100 次更新后该指针仍相同。清掉 `+0x28C` 后，原版可重新分配伴随对象并生成子弹；伴随对象缺失且空闲链头人为设 NULL 时不生成子弹。伴随对象完整退场/资源责任仍待查，不能从这些结果命名其全部职责。

### 登记与清理的配对合同

创建成功后的顺序是：写枪弹 owner、u8 计数加 1、从低槽到高槽找首个 NULL 并登记。原版创建器在四槽都非空时**不会回滚已经分配的子弹和已增加的计数**，因此不能把这个底层函数当成自行强制容量上限的安全接口。

`0x08035878` 则从最高槽往最低槽查找等于本对象的指针，只清第一个匹配项并把 u8 计数减 1；无匹配项不减计数，owner 为 NULL 时返回。函数本身不删除实体、不检查重复登记，也不把 0 减 1 饱和成 0。

人为构造的一致性反例：

| RAM 条件 | 原版运行结果 | 接入约束 |
| --- | --- | --- |
| 槽位正常且计数 1，请求退场 | 清槽、计数 0，下一次更新归还池 | 清理与实体回收要配对 |
| 用占位值替换原登记项，再让旧弹退场 | 不清占位值，计数保持 1 | 替换登记者必须负责计数所有权 |
| 同一对象重复放在最低/最高槽，计数 2 | 只清最高槽、计数变 1，留下重复指针 | 不允许重复登记同一实体 |
| 有匹配登记项但计数人为设 0 | 清槽后计数变 255 | 维护 u8 计数不变量，不能先任意清零 |
| 四槽为占位值、计数人为设 0，再发射 | 仍分配子弹并加计数，但无槽可登记；退场后计数未减 | 调用前必须协调上层门与登记空位 |

这些是**有意破坏一致性的夹具**，不证明正常游戏自身存在上述故障。占位 RAM 地址只在恢复快照中用于比较，不构成可永久分配内存的证明。

普通右向子弹在所选样本第 **22 次更新**进入状态 4、计数清零，第 **23 次更新**归还池。这是该位置和输入的实测时序，未归因于所有地形/寿命。人为设置对象 `+0x13=1` 同样经原版更新与清理进入状态 4。

对普通弹把命中状态 `+0x8C` 暂设 `0x1000`，原版没有立即解除登记：样本 VX 从 **1216 变为 -912**，即反向后的 3/4，实体仍在更新，计数保持 1，`+0x0A` bit 2 清零。不能把所有碰撞都概括成“马上销毁”，也没有据此宣称全部反射/属性弹轨迹已验证。

### 图形槽元数据与角色缓存

共享选择器的静态关系为：

```text
resource_slot = u16[0x08335E00 + 4*u8[owner+0x10]
                   + 2*(u8[owner+0x2B4] != weapon_id)]
```

已读前两行是 `[0,1]` 与 `[2,3]`，未普查全部合法 `owner+0x10` 范围。工厂用返回槽索引 `0x08335FD4` 的半字和 `0x08335FDC` 的字节，写实体 `+0x20/+0x22`；返回值大于 1 时还设置 `+0x0B` bit 6。本批只实测槽 **0/1**，对应元数据为 `0/192` 与 `1/1`，未验证 2/3 或据此认定四槽就是全部资源容量。

相同装备预置与副武器输入中，保持旧 `+0x2B4=0` 时仍选择槽 0；将该缓存字段预置为 1 后选择槽 1。只写装备配置 `+0x212/+0x213` 不保证资源选择字段同步。这里是显式 RAM 对照，没有替代原版菜单装备切换验证，更没有完成图块/调色板的加载、压缩格式或容量审计。

### Z3 投射物对照

参考同一固定提交的 [buster.c](https://github.com/mmzret/rmz3/blob/2a28700e0a74edd9578737c3b3435ced9d074045/src/weapon/buster.c)，仅静态对照。Z3 的创建函数有清旧剑调用，初始化增加 `bulletCount`，删除函数递减计数并删除实体；本样本 Z2 则在创建器增加计数，按匹配登记槽解除计数，退出回调再归还池。两者可以对应“创建/初始化/更新/删除”的职责，但不能照搬计数修改时机或所有者结构偏移。未在本机编译验证 Z3 C，也没有执行 Z3 ROM。

## 第三批：调色板请求、共享与发布

新增深入 **4 个函数**，累计 **14/15**。只调查上述剑/枪弹的共享资源前置，不重开输入缓冲、连招、评分或 Boss。静态依据是匹配原版 ROM 与正式汇编，动态依据是完整原版运行；特殊条件只写模拟器 RAM，没有函数替换、跳板或 ROM 补丁。

| 函数 | 有限职责 | 证据 |
| --- | --- | --- |
| `0x08037DEC` | 把 owner 和第2参数转为主侧调色板请求 | 静态调用 ABI；复用已研究剑创建器调用点 |
| `0x08037E0C` | 按 owner 的 `+0x10` 与侧号索引请求槽 | 静态；仅列前两行，不推定所有合法角色值 |
| `0x080390A8` | 向所选槽写 u16 请求值 | 静态；运行夹具从同一请求表开始 |
| `0x08039020` | 依次处理四槽差异、复制调色板到缓冲，再调度武器池 | 静态及槽覆盖/缓存/物理调色板对照 |

### 实体图形槽和调色板请求槽是不同索引

前批 `0x08037DC8` 使用表 `0x08335E00`，条件包含 `owner+0x2B4` 与武器编号比较；它给实体的图块基址/调色板编号选元数据。

本批 `0x08037E0C(owner, side)` 则读：

```text
request_slot = u16[0x08335E08 + 4*u8[owner+0x10] + 2*side]
```

前两行同为 `[0,1] / [2,3]`，但这是**另一张表、另一套选槽条件**。`0x08037DEC(owner, palette_index)` 固定 side=0，把截断为 u16 的 palette_index 交给 `0x080390A8`。后者写 `u16[0x02000038 + 2*u16(slot)]`，本身没有验证 slot 或 palette_index 范围。剑创建器的第6参数走此链，不能把实体最后选中的槽或 `+0x22` 直接当调色板源索引。

本批普通剑样本的实体图块基址为192、调色板编号为1；普通枪弹为0与1。二者运行时请求表均为 `[0,FFFF,FFFF,FFFF]`。这些正常流程样本只验证已有对象继续正常生成与使用同一颜色组；没有因为请求值不变就声称动态确认了某个请求写入点。

### 四个逻辑槽只指向两个不同的颜色组

`0x08039020` 按槽 i=0到3遍历，比较：

```text
current[i]   = u16[0x02000030 + 2*i]
requested[i] = u16[0x02000038 + 2*i]
```

不等时先更新 current，再以 `0x08335FE0 + 32*requested[i]` 为源，向 `0x03002CC0 + 32*u8[0x08335FDC+i]` 复制所选颜色。表 `0x08335FDC` 四项是 **`[1,1,6,6]`**：

| 逻辑请求槽 | RAM 颜色缓冲 | 实际 OBJ 调色板位置 |
| --- | --- | --- |
| 0、1 | `0x03002CE0`，32字节 | bank1，`0x05000220`，32字节 |
| 2、3 | `0x03002D80`，32字节 | bank6，`0x050002C0`，32字节 |

这是**本条武器路径四槽中的共享关系**，不是全游戏只能使用两组调色板，更不是 VRAM 总容量结论。源索引0/1是已测试值，没有据此声称源表只有两项。无效索引未运行；静态可见这几个局部接口没有自带边界保护。

### 原版执行中的覆盖、缓存与发布

同一序章下共8组条件（含空白对照和两个已有攻击样本），详见[第三批机器证据](semantic-data/stage2c/resource-third-batch-20261108.json)。从开机重新生成基线，不加载用户存档。

| 条件 | 实测结果 | 对新攻击接入的约束 |
| --- | --- | --- |
| 槽0请求0→1，两次更新后再恢复0 | 缓冲先变化，物理调色板在下一次更新边界才出现对应值；恢复也相同 | 请求写入不等于立刻可见，所选样本存在一次更新的发布延迟 |
| 槽0/1均标为待刷新，分别请求0/1 | 两个缓存都更新，但同一bank1最终是源1 | 同一更新内，后处理的脏槽覆盖先处理者 |
| 槽2/3同样设置 | bank6同样最终为源1 | 第二对槽也存在同样别名 |
| 槽1缓存/请求均为1，仅槽0待刷新为0 | 两缓存保持不同请求值，最终bank1却为源0 | 不是永久“高槽优先”；最后实际刷新的脏槽赢，缓存不代表独占所有权 |
| 槽0缓存/请求均为0，人为把bank1缓冲改为源1 | 缓冲未自动恢复0，物理调色板随后也是1 | 相等缓存会跳过重载，另一个使用者改色可能留下过期缓存 |
| 普通剑、普通枪弹各一次 | 正确池/类型表/owner下生成对象，颜色编号均1 | 证明已有样本，未替代任意新图块/配色的接入测试 |

上述颜色夹具没有改攻击输入或对象状态。逐次与**同输入、同更新次数**的空白对照比较，VRAM的96KiB内容散列完全相同，OBJ调色板中变化不越过对应32字节颜色组。它们验证了颜色更新不必上传新图块，不能作为新图块加载完成或显存有空余的证明。物理发布仅观察到所选更新边界，不把它扩大成所有显示模式、菜单或关卡中的固定时序。

本批没有新增深入共享复制函数 `0x080EEF68`、全局调色板发布器或图块加载器；复制范围和最终颜色由原版运行对照验证，不声称已解释其全局实现。Z3本批不新扩展函数：沿用前两批固定提交的剑/枪弹对照，不因Z3也有tile/palette字段就照搬加载时机或布局。

**接入结论**：新攻击需要协调已有共享颜色组的所有者与刷新责任；四个逻辑请求槽不是四份独立颜色资源。对象池/登记槽、图块基址和调色板请求必须分别维护。仍不能指定任意图块、任意颜色源或把一个新攻击的资源清理交给缓存碰巧恢复。

## 第四批：所选剑动作的图块刷新入口

唯一新增深入函数为 **`0x080128D4–0x08012A06`**，累计 **15/15**。本批解释调用边界和实测条件，未深入底层上传器。证据见[第四批记录](semantic-data/stage2c/tile-fourth-batch-20261108.json)，完整原始对照写 `build/stage2c/tile-refresh-20261108.json`。

### 静态入口与缓存合同

该函数推进动画，通过对象 `+0x6C/+0x70/+0x71` 取得当前绘制编号，保存到 `+0x4E`。只有 `flags_b(+0x0B)` bit2 为1才继续资源刷新路径。它按对象 `motion_id(+0x1E)` 查询 `0x084AD300`，再按当前绘制编号取记录的第3字节，作为资源键；若与 `cached_key(+0x1F)` 相同，就不再提交图块刷新。**绘制编号变化，不代表资源键必然变化。**

在已测试的 motion_id≤`0x8F` 路径中，选择记录与传给 `0x080027AC` 的目标位置为：

```text
entry = 0x084CC680 + 4*motion_id
descriptor = entry + u32[entry] + 12*resource_key
tile = u16[0x0202E790 + 2*motion_id] + u16[entity+0x20]
dispatch_destination = 0x06010000 + 32*(tile - (u16[descriptor+6] >> 6))
```

随后把 tile 的低10位写进对象绘制属性 `+0x48`。未设置 `flags_b` bit5时，另计算并写入颜色属性。本批没有扰动颜色属性分支，也没有验证高 motion_id 的附加调色板加载分支。动画推进、底层 `0x080027AC`、附加颜色加载 `0x08002AEC` 均只登记依赖，不把它们算作已解释。

### 四条件原版运行对照

从开机生成原有序章基线，把已拥有的剑置于主槽；一次攻击后第9次更新保存**本次新建**RAM快照，再分别运行四条件。身份固定为武器池句柄 `0x0202F070`、类型表 `0x08336060`、类型3、生命周期表 `0x08336564`、所有者Zero和更新回调 `0x0803A409`。

当时 motion_id=`0x58`、资源键4、图块基址192、RAM偏移8，绘制属性 tile=200。之后四次更新中绘制编号为4/5/5/5，资源键均保持4。

| RAM条件 | 绘制属性和缓存 | 完整96KiB显存对照 |
| --- | --- | --- |
| 空白对照 | tile=200，资源键4 | 基准 |
| 只把实体图块基址192改为256 | tile仍200，资源键4 | 四次更新均与基准完全相同 |
| 改基址并把缓存键设为FF | 第一次更新tile变264，缓存键恢复4 | 第一次仍与基准相同；第二次起有474个差异字节，全部符合`+0x800`的目标地址平移 |
| 改基址、失效缓存，再清bit2 | tile仍200，缓存键保持FF | 四次更新均与基准完全相同；绘制编号仍在推进 |

成功条件的静态提交目标由 `0x06011800` 变为 `0x06012000`。实际观察到差异的范围是 `0x06012139–0x060131DF`，共474个字节；逐字节与原位置减`0x800`后的基准值比较均相等，整个显存其余位置没有差异。这是**完整显存的差分结果**，474不是总上传字节数，范围也不是一个连续写满的缓冲区。

初次调查中，“描述符后数据是连续原始图块、可以整块比对显存”的简化假设不成立；窄窗口检查还会漏掉窗口之外的变化。本批改用全96KiB差分和同更新次数的地址平移对照，保留该负例，不擅自命名底层格式、压缩方式或完整搬运范围。

**接入约束**：仅改实体图块基址，不保证现有缓存触发重载，也不保证绘制属性同步。刷新请求和实际显存可见仍有更新边界间隔。`256`及对应目标区域只是可恢复快照内的测试值，**没有证明是可供改版占用的空闲显存**。本批没有实现安全分配器、资源卸载或新招式。
