# 项目文字引用、字符渲染队列与字形证据

2026-10-29。只读取本机美版基线ROM及已有汇编；解码结果与像素证据写入docs/semantic-data，不运行重建或改变提取器。

## 名称与储能用途互证

D5B80(entity无关的itemId参数)从12B描述符+4取u16引用，查0834C47C半字偏移表，加文本基址0834C9E4，再以坐标(0x11,7)交DE510。D5BBC类似使用+6说明引用，某些持久位图状态改用引用0x11F。

项目6：名称引用0x69，地址0834CF8A，拉丁解码为Estan。说明引用0xCD，地址0834D278：`I turn` / `into a` / `Sub Tank`，末尾字形E2保留为未知标记。

项目7：名称引用0x6A，地址0834CF90，拉丁解码为Peatan。说明引用0xCE，地址0834D290：`I can be` / `your` / `Sub Tank`，同样保留E2标记。

这两条说明与0x80异步动作、最终37A9C增加B组储量槽的代码互证，支持把B组解释为由这两个项目变成的Sub Tank。此时“储能罐”已不只是从数值行为推测。正式C符号仍不改名，因为本轮仅做语义研究。

同一文本池的0x174含`I need Energy Crystals`，与成长余额转移解释相容，但尚未从显示调用者证明这个具体引用就是EC544的余额标签。不要仅凭同池词语把所有数值字段正式重命名。

0xB5/0xB6/0xB7分别读作Nurse、Animal、Hacker；与三个27项目组的对应关系还应由类别显示调用者确认。本轮列为已解出的文本，不将邻接顺序当作唯一语义证据。

## 码表验证与导出限制

[字形证据图](semantic-data/font-latin-evidence.png)直接依DE318使用的ROM寻址公式读取4bpp图块，以非零像素显示。图按16列排列，前4行代码00..3F，后2行D0..EF；每字形8×16，4倍显示。已在本轮查看像素图，核实空格、数字及大小写拉丁字母排列：

- 00 → 空格。
- 01..0A → 0..9。
- 0B..24 → A..Z。
- 25..3E → a..z。

其余字形未全部人工映射。导出保留`<GLYPH_...>`，不删除或猜测标点。81项目中的4个名称仍含未知字形或扩展标记，其余名称在该局部码表域内可完整转写。

[项目文字数据](semantic-data/item-text.json)包含81项目的名称和说明、引用id、实际ROM地址、原始字节（含终止字节）、已知字符转写和控制码标记；含基线SHA1。它不是完整游戏文本汉化工具，也没有解动态RAM插入字符串。

## DE510文字队列布局与容量

全局0202F0A0控制文字渲染。DE510不是立刻绘制，而是把stringPtr、x、y、最大字符数写入队列。正常count<=95时追加，count>95不追加；它不检查负count，正常初始化/调用者须维持有效域。DE564接收显式字符限制，DE510使用0xFFFF。

| 全局相对偏移 | 大小 | 用途 |
|---|---|---|
| +0 | u32 | 目标tilemap基址 |
| +4 | s32式读取计数 | 文字请求数，正常最大96 |
| +8..0x187 | 96×u32 | 字符串指针 |
| +0x188..0x1E7 | 96×u8 | x坐标 |
| +0x1E8..0x247 | 96×u8 | y坐标 |
| +0x248..0x307 | 96×u16 | 每请求字符限制 |
| +0x308..0x587 | 80×8B | 字形缓存节点 |
| +0x588 | ptr | 本轮活跃字形链 |
| +0x58C | ptr | 可复用的旧字形链 |
| +0x590 | ptr | 空闲缓存节点链 |
| +0x594 | ptr | F9动态插入字符串指针 |

DE1FC初始化80个缓存节点和链头，并清文字队列计数。DE28C先把本轮活跃节点移至可复用链，再逐请求按tilemap+2*(y*32+x)定位，交DE818绘制，最后清请求计数。不存在“读取DE510返回就代表文字已经显示”的保证。

## DE818控制码的代码级含义

普通字节00..EF作为字符字形码。下列行为由DE818直接读取，区别于仅凭字符串样本猜测：

| 字节 | 行为 |
|---|---|
| F0,n | 消耗下一字节，形成扩展字形码0xF0+n |
| F1 | 清当前字形/样式掩码 |
| F2 | 掩码设为0x200，影响字形变体寻址 |
| F7,n | 掩码设为低16位(((n+2)<<12)|0x400) |
| F3..F6、F8 | 在本绘制器中跳过下一参数字节；不在本轮赋更高层游戏含义 |
| F9 | 用全局+0x594指针递归绘制插入字符串，并调整剩余字符限制/位置 |
| FA/FB | 本函数未见额外有效绘制分支，继续推进指针 |
| FC | 换行：从保存的行首加0x80字节到下一文本行 |
| FD..FF | 循环入口直接停止，不继续当普通文字读取 |

DE818按charLimit限制可处理字形数量；递归插入未见通用循环/深度检查，需要有效动态指针。队列指针及流也无通用长度检查。研究解码器使用2048字节有界读取以防误判表边界，未知码保持标记，不模拟动态状态。

FC的0x80字节移动相当于tilemap两行（每tilemap行0x40B），与8×16基本字形的高度对应。普通字形在当前tilemap行和下行写入相邻两tile编号，正常横向前移一列；扩展双列字形另有第二列路径。

## 字形缓存与上传

DE954优先在活跃链按glyphCode&0x0FFF查找，然后查可复用旧链，找到后移入活跃链；没有命中则取空闲节点，必要时回收旧链节点。无可用节点时返回NULL，DE818停止当前绘制并返回剩余字符预算。节点+4存字形码，+6为tile号及0x8000脏标记；新字形会置脏，DE318负责上传。

DE318对普通<=0x1FF字形使用：

```text
offset = (glyph & 0xFFF0)*64 + (glyph & 0xF)*32
upperTile = ROM[080EF82C + offset .. +32)
lowerTile = ROM[080EFA2C + offset .. +32)
```

正常一个字形的上下tile均为32B，按GBA4bpp的每像素半字节读取。200..3FF变体路径对读出字数据移位处理；400以上使用另外的资源基址和宽字形路径，不能把全部编码范围当作同一个ASCII字库。

## 名义代码区边界的直接反证

普通字形表按上述公式覆盖080EF82C起的0x8000B，即到080F782C（不含）的一块字形数据。像素图及渲染器引用互证这是数据，而不是手写函数。

现有覆盖率分母使用ROM[0,F0000)作为名义代码区；此范围与该字体相交[EF82C,F0000)，共0x7D4=2004字节。这为“代码区边界是启发式、含数据”的具体证据。不能将89%左右往返构建覆盖直接解释成纯代码/真实函数覆盖，更不能当作语义完成百分比。本轮只记录边界证据，未修改候选队列、清单、后台统计或任何ROM字节。
