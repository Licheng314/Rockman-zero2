# 捕获登记碰撞回调（0x08079748）与类型-状态二维分派表

本轮承接 [发射初始化](semantic-parent-launch-init.md) 与
[捕获协议](semantic-parent-capture-protocol.md)，从 0x0833D990 指针表切入，
解码捕获登记的碰撞回调本体，并与协议报告的推断逐条互证。
证据来自原 ROM 字节 + capstone 反汇编（校验脚本见
[semantic-data/parent-launch-786f0-check.py](semantic-data/parent-launch-786f0-check.py)，32/32 通过）。

## 0x0833D990 = 类型 × 状态 二维处理函数分派表

结构：第一层 0x0833D990[0..108]（109 项，106 唯一，3 组重复项）指向第二层
Thumb 函数指针数组；**第一维 = 对象类型（e[9]，0x080AFC70 守卫过的同一字段），
第二维 = 阶段 D**。证据：

- 786F0 取 `表[e[9]]` 后读 `[ptr+4]`（D=1 = 向外阶段）存入 e[0x14]——按 D 索引；
- 几乎每型的 fn[3]（D=3）共享：83 个类型共用 0x08065A05，另 3+2 个类型各用
  另两个共享值——状态 3 处理器按类型分组共用；
- 第二层数组长度不定（5~284 项），即各类型的状态数不同；
- 0x08065A05 本体：`e[0xA] &= 0xFE` 后按 e[9] 查表——状态退出处理，非平凡函数。

**旧 funcdb 的 SWI 名称表勘误确认**：graphic-transfer 报告实证 SWI 0x12 = LZ77UnCompVram、
0x15 = RLUnCompVram（压缩头 bit 分派），据此 GBA BIOS 编号为
09 ArcTan / **0A ArcTan2** / 0B CPUSet / 0C CpuFastSet / 11 LZ77Wram / 12 LZ77Vram /
13 Huff / 14 RLWram / 15 RLVram。EEF5C-EEF78 区域 = BIOS 调用包装器表 + call_via 助手，
不是数据噪声也不是手写汇编。旧 funcdb 的 0x0A-0x12 标签需按此修正。

## 捕获登记回调 0x08079748（786F0 注册到六段链 +0x24）

签名 `callback(r0 = 段对象)`，六段附属链各自的 +0x24 槽都注册了它。完整逻辑：

```
r2 = 段
if (!(段->unk14 & 4)) return            ; 该段本轮无碰撞命中
r0 = 段->unkC                           ; 碰撞系统登记的对方实体
r4 = r0->unk2C                          ; 对方->unk2C = 捕获候选
if (r4->unk9 != 0x22) return            ; 候选类型必须是 0x22
r3 = 段->unk2C                          ; = 飞行对象 S（786F0 写入 [e+0x74+0x2C] = e）
if (S->unk2C != 0) return               ; 已登记过，不重复捕获
S->unk2C = r4                           ; ★ 登记目标对象指针
S+0xD = 1                               ; 状态字节
S+0x13 = 0x10                           ; ★ 超时重置为 16 次（协议报告"等待16调用"实证）
S+0xB4 = r4->0x54 - S->0x54             ; ★ B4 = 目标-自身的 X 相对偏移
S+0xB8 = r4->0x58 - S->0x58             ; ★ B8 = Y 相对偏移
r4->unkD = 4                            ; 目标进入状态 4（被捕获）
r4->unkE = 0
r4+0xB4 = S                             ; 目标的 B4 = S 回指针（跟随用）
```

与 [capture-protocol](semantic-parent-capture-protocol.md) 报告的三条推断逐条互证：

| 报告推断 | 本轮字节级实证 |
|---|---|
| "实际碰撞回调登记目标" | `S->unk2C = r4`，候选类型 = 0x22 |
| "等待 16 调用后返程" | `S+0x13 = 0x10`（恰为 16） |
| "目标按相对偏移跟随" | `S+0xB4/B8 = 目标-自身`；目标 `+0xB4 = S` 回指针 |

另外确认：捕获候选经 **碰撞系统的 unkC 配对字段**取得（与
[entity-collision-pairing](semantic-entity-collision-pairing.md) 衔接），且类型 0x22 的
目标自身也要进入状态 4/0xE 清零并携带回指针——"跟随"是双向链接。

0x0807BD98、0x0807CDBC 是同构回调（同样读 [r2,#0x14] 与 &4 测试），
属其他类型组的捕获回调——该模式按类型组重复。

## e[0x14] 的角色修正

786F0 把 fn[1]（D=1 向外阶段处理器）存入 e[0x14]。本轮未找到独立的
"每步调 e[0x14]"分派点——更可能的机制：fn[1] 本体（如类型 0 的 0x08065BF9）
就是向外阶段的每步处理器，碰撞检测与捕获登记内嵌其中，0x08079748 是它们共用的
登记助手（经 S+74 链的 +0x24 槽被段回调）。此推断与六段链各自有碰撞组件的事实一致。
**e[0x14] 的实际调用点仍未定位**，保留为未解决项。

## 已验证范围与接续

本轮证据 = ROM 字节级结构解析 + 既有报告互证，未执行任何代码、未做全场景验证。

（第二层数组长度不定），表区总边界未精确圈定。

③目标类型 0x22 的身份鉴定（结合 type23-spawn 的类型清单）。
