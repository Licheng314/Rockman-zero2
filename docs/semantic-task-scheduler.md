# 协作式任务调度与游戏状态循环

2026-10-29，只读分析已有汇编并核对原ROM。未修改运行工具或正式源码，后台提取继续。

## 已确认的数据布局

调度器00FA8与让出助手01098共同指向三项任务表，基址0x03002A68，步长0x18。01098先读取03001760+0x1350=03002AB0中的当前索引，再取03001760+0x1308=03002A68加index*24的任务项。

| 项内偏移 | 本轮已证实用途 |
|---|---|
| +0x00 u8 | 状态/标志：精确值2可执行；bit0或bit3使调度器跳过；bit2触发倒计时处理 |
| +0x01 u8 | 请求重新初始化任务入口的标志，非0时调01064重置项再启动 |
| +0x02 u16 | 等待的调度轮数；01098/010DC写入 |
| +0x04 u32 | 新任务入口或暂停任务的恢复地址 |
| +0x08 u32 | 暂停任务的栈指针 |
| +0x0C..+0x17 | 本轮未完整鉴定，不臆造字段 |

当前调度器栈指针通过全局0x02000004交换。01064使用08312318的u16栈偏移表，为任务项设置初始SP；它不是动态堆分配。

## 切换原语的准确范围

002DC(task, resumePC, taskSP, schedulerSPOut)：保存调度器r4-r11及LR，将当前SP写到r3指向位置，切换到任务SP，恢复任务r4-r11，以resumePC进入任务。任务初次启动和从让出点恢复依赖01064/00300构造的栈布局。

00300(resumePCOut, taskSPOut, schedulerSP)：保存任务r4-r11，将调用时LR写入resumePCOut，将任务SP写入taskSPOut，再切回调度器SP并恢复r4-r11及LR，返回调度器。这里直接改SP，不能等同于普通C函数回调。

00328(schedulerSP)：丢弃当前任务执行栈并恢复调度器保存的上下文。0115C使用此原语完成任务入口替换，而不是普通return后继续旧代码。

## 调度器00FA8

每轮把当前索引置0，从任务项0扫描到2：

1. 状态字节含bit0或bit3则跳过。
2. 状态含bit2时，读取+2半字；如果其有符号读取值等于0，直接设置状态2；否则按16位减1，结果为0才设置状态2。代码仅检查是否等于0，不承诺负数等待值被安全拒绝。
3. 状态精确等于2时可执行。如果+1非0，先用当前索引及+4地址调用01064重新构造入口。
4. 以+4地址和+8栈经002DC进入任务。任务让出后，调度器继续下一个槽。
5. 扫描3项后，03001760+0x1300的计数加1；03001760+0x1304非0则继续新一轮，否则退出。

让出01098(n)作用于当前索引；n非0才将状态置4、写等待半字、调用00300。n==0直接返回，并不主动让出。010DC(task,n)逻辑相同，但项指针由调用者提供。

01100将当前项状态置1并让出，暂停其后续调度；0113C(index)只在原状态不等于1时写1。注意0113C不会保存任务栈，它是标记操作。

0115C(newEntry)将当前项+1置1、+4写newEntry，再用00328返回调度器；下次执行时01064用新的入口重新初始化栈。

## 启动与游戏任务安装

00438：初始化后用01064(0,0051D)与01064(2,005FD)建立槽0和槽2，再调用00FA8。

0051C：完成初始化，让出一次后经0115C(0x080DFB91)替换当前任务入口。因此不能把0051C直接称为进入E0E3C的入口。

DFB90：上下文基址0202F680，按context[4]索引ROM0835E2F0起的外层模式表，每次回调后01098(1)让出。

原ROM E0862：读取池E08B8中的Thumb指针080E0E3D，随后01064(1,entry)，明确安装到任务槽1。该段所在完整函数的前置状态尚未穷举；不能只由地址附近另一次0115C调用误认它在替换当前任务。

E0E3C：对传入任务相关结构调用011DC后，使用固定游戏上下文0202F8E0。每轮按context[0]索引0835E3B4起表，回调后01098(1)，再回到循环。它是槽1内的游戏模式协作循环。

0835E3B4的第0项为E3DC9；E3DC8继续按context[1]索引0835E408。第4项是E4391，后者在符合条件时调用E5AF4。得到完整链：

```text
scheduler00FA8 slot1
 -> E0E3C context=0202F8E0
 -> table0835E3B4[context[0]] (index0=E3DC8)
 -> table0835E408[context[1]] (index4=E4390)
 -> E5AF4 recovery queues (受早退及模式标志影响)
 -> yield01098(1) on return to E0E3C
```

## 与屏幕刷新节拍的关系

槽2的005FC循环中有04000006读取并与0xA1比较，以及03001590相关计数字节轮询；循环尾调用010DC(task,1)。它提供显示/扫描线同步机制的证据。没有看到直接BIOS等待调用，不能把01098命名为VBlankIntrWait。

本轮确认了每次恢复更新后会经游戏任务让出，以及等待1在下一次扫描任务项时可恢复。仍未证明调度每轮严格一帧：槽2轮询、硬件中断对计数字节的更新和模式早退都可能影响节拍。文档仍以“每4次有效E5AF4调用”表述恢复周期。

## 与零值和扣减语义的连接

47E9C(entity)：读取entity+0xC8指针指向对象的+0xD2字节作为扣减量，对entity+0xA4半字做减法；对低16位结果作有符号判定，负值钳0，写回；结果0时entity[0x11]=1。准确机器语义是先取差的低16位再判符号，不是对任意大整数都成立的数学max(0,x-d)。正常小正数域才可简化成饱和扣减。

该函数还检查entity+0xB4关联对象的状态bit0x200及+0xA4零值，必要时清关联指针，之后处理效果对象和动作回调。Thumb指针位于ROM0833AC58。本轮没有把其具体对象种类等同于玩家。

28A28末段直接将实体+0xA4清0，同时清+0x8C/+0x90及+0x94部分状态、清实体标志bit2，并把EC30+8写成(flags & 0xFFFE)|0x10。该路径与恢复抑制逻辑再次互证；尚不为整个函数编造游戏情节名。

## 研究限制与下一步

- 调度上下文和任务项是两套结构，不能把0202F8E0的状态字节和03002A68的任务状态字节混为一体。
