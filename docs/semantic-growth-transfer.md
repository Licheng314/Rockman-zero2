# 成长投放、资源余额与数值提交时序

2026-10-29，只读语义轮。该报告将项目成长域与此前的“第二种16位资源”连接起来；不改变后台提取、C源码和ROM构建。

## 余额字段及接口互证

EC544提交时从root+0x75B8取实体，对entity+0x1FC处记录的+2半字扣减所选数量，即余额位于entity+0x1FE。相同数量加入entity+0x24A+2*growthIndex的累计值。

22A54以08333B40为分派表。首项的真实入口为080379DC，指令返回entity+0x1FE地址。2306C通过22A54取指针，对此半字做饱和增加；首分派索引使用08333B34中的半字上限0x270F=9999。E5AF4的全局E150计时路径调用2306C(entity,4)。这把资源补充、余额指针、成长支出三条独立路径接到同一字段。

可操作级命名为“可用于成长的资源余额”；界面文本尚未解码，不直接断言具体游戏货币名称，也不把索引0的9999上限推广到所有实体种类。

## 项目选择与输入准备

EC138通过D6094从分类/索引选出项目id。确认条件包含id1..81、233位图中对应位为1、D5A34返回0（尚未成长完成）。通过后保存项目id到root+0xDDE、描述符成长索引到root+0xDDF，进入投放子流程。

EC2A4会再次检查合法id、233位和未完成；成功后：

```text
current = D5A98(entity,id)
threshold = D5ADC(entity,id)
remaining = threshold - current
maxSelectable = min(remaining, load16(entity+0x1FE))
selectedAmount = 0
```

remaining保存在root+0xDE4半字，maxSelectable在+0xDE2，selectedAmount在+0xDE0。root+0xDDA是当前十进制位，+0xDDB是按余额计算的位数，+0xDDC参与显示提示计数。合法阶段下threshold>=current是正常流程约束；函数没有通用检查所有损坏存档状态。

EC384负责数值输入：按选中位计算10^digit作为步长，加减后钳到0..maxSelectable，边界按键还有0/最大值切换行为。确认时selectedAmount必须非0，否则请求编号4的反馈，不提交。取消输入阶段则返回项目选择，不改变余额和累计值。

## 实际提交早于反馈动画和阶段推进

EC528用root+4的signed16子状态查0835E990：

| 子状态 | 函数 | 已确认作用 |
|---|---|---|
| 0 | EC544 | 一次性数值提交，随后进入反馈 |
| 1 | EC59C | 等待确认或显示当前阶段提示 |
| 2 | EC664 | 主反馈进度，在边界调用D59AC推进成长阶段 |
| 3 | EC708 | 继续反馈并检查结束，切到状态4 |
| 4 | EC734 | 完成提示及确认返回 |

EC544入口先把root+4设1，再读取root+0xDE0金额，执行：

```text
accumulator[g] = low16(accumulator[g] + amount)
balance = low16(balance - amount)
```

它没有再次核查amount<=balance，没有饱和扣减，也没有对增长加法另加上限；安全数值域来自EC2A4/EC384及两者之间余额保持有效的约束。不能把EC544当作可任意从外部调用的通用扣款接口。

提交后EC544调用EC59C，此时累计值和余额已经改变。反馈动画不会再逐点扣资源，不能用动画进度替代账面数值。

EC59C确认时，若amount<remaining，直接将root[2]=1、root[3]=1、root+4=0，回到选择流程；此次支出/累计保留，但不会强行升级。若amount>=remaining，进入状态2，并初始化反馈的进度方向及循环数。

EC664在主反馈向上达到0x30时调用D59AC(entity,id)，真正更新阶段；这个值是反馈计数阈值，不是投放金额48。EC59C将重复计数初始化为2，故先两次0x18小峰值，再在重复计数0时到达0x30主峰值；主峰值才调用D59AC，最后经EC708/EC734收尾。所述计数以该函数被调用次数为单位，未证明全部情况下与屏幕帧一一对应。

因此这不是事务式单步“付款并升段”：先变余额/累计，再经反馈调用更新阶段。正常输入退出与外部异常强制离开须区分，不对任意中断状态保证自动退款或自动补升段。

## 项目6/7的具体例子

它们的成长索引5/6、最大阶段1、阈值400。在新获得且阶段/累计均0的正常状态：

- 余额>=400时，maxSelectable=400；确认400使累计增加400、余额减少400，之后在反馈边界把阶段从0推进到1。
- 余额100时，maxSelectable=100；投放100后累计100、余额减100，阶段仍0。下次remaining=300；不是又从400重新开始。
- 余额0时maxSelectable=0，确认条件不成立，不应正常进入EC544的非零提交路径。
- 阶段已1时，EC138/EC2A4的完成检查拒绝继续进入投放选择。

这些是直接由代码和ROM表推导的例子，不声称已通过模拟器运行。400现在可解释为该成长段的累计资源需求，具体货币/投喂物名仍待显示/资源链核实。

## 描述符+3字段的新增解释

EC59C和EC734读取描述符+3，以其为索引取一张指针表，再按当前成长阶段读取显示引用。此字段至少参与“成长提示类别”的选择。此前清单把+3保留未知仍保留原字节；现补充其已确认的显示用途，不把它直接等同于成长段数或价格等级。

## 正常流程与异常边界

- 输入取消发生在提交前，可保持数值不变；提交后的确认/反馈不是取消退款接口。
- D59AC只推进阶段，不扣累计值；partial投放累计可以跨次保留。
- 61FC重复获得会重置该项目累计/阶段，但不退还先前扣除的余额；调用方应使用获得去重约束，不能擅自称重复发放无副作用。
- 成长阶段、已使用位图和三项配置资格仍独立：达到成长上限只是配置的一项前置条件。
- 后续沿ECAD4/ECD68显示引用与文本读取器核实游戏内名称；对异常模式退出和保存时机继续单独分析。


## 显示层补证

[菜单名称报告](semantic-menu-labels.md)确认ECAD4在Cr标签旁显示entity+1FE；400因此是此界面Cr余额的单段累计需求。Energy Crystals全称仍作为强推断，未把文本池174的存在当作该显示调用链证据。项目6/7的成长提示类3记录168/16C已核实。ECD68属调色板反馈，不能继续作为金额文本显示函数处理。

## 反馈顺序与显示职责修正

[调色板反馈报告](semantic-palette-feedback.md)依据EC59C初值与EC664分支确认：先两次24小峰值，再48主峰值升段，最后回落退出；正常D59AC在第144次EC664调用，反馈共192次调用，不当作帧数。ECD68使用ROM原色局部插值，并写软件全局颜色系数；02994随后发布到硬件。此前“大峰值之后重复小反馈”的顺序描述已修正。

## 输入语义补证

[输入报告](semantic-input-state.md)确认EC384的三个输入字段：+4新按用于确认/取消及数位切换，+0按住加+6逐键连发用于金额增减。最大值新按Up绕回0、0新按Down跳最大值，而持续按住到边界的连发保持钳位。默认连发24/4以采样次数计，不直接换算屏幕帧或时间。
