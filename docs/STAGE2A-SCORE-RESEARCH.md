## A1：分项输入 → 结算 → 总分/等级 数据流表

结构：`0x0202EBF0` = 本关结算工作区（`+0x00` 存指向任务记录 `0x02036BB4` 的指针）；`0x02037CF0` = 玩家档案（武器/EX/精灵队列）。任务开始 `0x080148B4` 写任务 ID 到 `u16[0x0202EC30]` 并经 `0x080141A4` 初始化工作区。十进制数值以十进制注明。

| 结算显示行 | 工作区字段 | 宽度 | 写入者/时机 | 计分公式（0x080141FC） |
|---|---|---|---|---|
| MISSION (加分项) | +0x07（显示副本 +0x16） | u8 | 初始 20；事件扣分（0x080C7340/0x080CE768 各 -2，下限 0）；任务 2/3 结算时按 `0x0202EBB0+6/+7` 位重算 | 原值入总分 |
| CLEAR TIME | +0x08 | u32 帧数 | `0x080E4390` 每帧 +1，上限 359998 | `秒 = 帧/60`（`__udivsi3` 0x080EF2B8）；`超出 = 秒 - 时间表[任务]`（0x08325DC0，任务1=130s）；超出 ≤0 → 20；≤199 → `20-(超出+9)/10`（即 20-⌈超出/10⌉）；否则 0 |
| ENEMY | +0x0C | u16 击破数 | 约 45 处敌人死亡处理（≤9998 时 +1） | `q = 击破/(死亡+1)`；q=0 → 0；`n = 期望击破表[任务]×10 / q`（0x08325E04，任务1=40）；n≤10 → 15；n>24 → 0；否则 `25-n` |
| DAMAGE | +0x0E | u16 受伤累计 | `0x08014360`：每次伤害请求量 ≤64 且总和 ≤9999 才累加（见[受击消费者研究](semantic-hit-consumers.md)） | 0 → 15；>75 → 0；否则 `15-((受伤-1)/5)` |
| RETRY | +0x14 | u16 死亡数 | `0x080E4BE8` 死亡 +1（≤99），同块扣残机 | 0 → 15；>4 → 0；否则 `15-3×死亡` |
| ELF | +0x10 | u32 辅助/精灵使用数 | 结算场景状态1（`0x0801CE5C`）调 `0x080D61B8`：返回 `u8[档案+0x283]+u8[+0x284]`，随后 `+0x283 += +0x285`、`+0x284/+0x285` 清 0（三槽滚动队列） | `15-使用数`，下限 -100（字节存为 0x9C 回绕） |
| TOTAL | +0x05 | u8 | 结算时六项按 **u8 加法（mod 256）** 求和写入；`u16[0x02036BB4+0x0A] += 该字节`，`+0x10`（通关数）+1 | 上表六项之和（mod 256） |
| RANK | `0x02036BB4+0x01` | u8 | `avg = scoreSum/clearCount` 与阈值表 0x08325E48（46/56/66/76/86/96）顺序比较 | 0..6 = F/E/D/C/B/A/S（等级字母表与 Z3 相同，见对照节） |
| CODE NAME / 类别 | `0x02036BB4+0x02`(当前)/`+0x03`(上关) | u8 | `0x08014384` 结算末段：类别（0-8）由最弱分项决定（时间子分 >18 → 类1；=0 → 类2；击破/受伤/死亡/加分各有判定；rank=6 强制类 0）；四项收集计数（+0x1C..+0x22，写入者 0x080355C8 族）求和 ×7/10 定档位 1-5，`新值 = 0x08325E64[档位×8 + +0x34+档位]` | 档位/类别 → 称号与 EX 档位晋升（0x02036BB4+0x34 起计数） |

读写时机：+0x08/+0x0C/+0x0E/+0x14 在任务运行中实时累计；+0x10 与全部子分在结算场景状态1一次性计算（先 `0x080D61B8` 聚合，再 `0x080141FC` 评分，再 `0x08014384` 档位/类别）；结算显示由 `0x0801D1D8` 逐项滚动展示（次序：MISSION、时间、ENEMY、+0x17、+0x18、DAMAGE、+0x19、RETRY、+0x1A、`[0x02036BB4+0x4C]`、ELF、TOTAL、RANK）。

动态验证：复跑脚本以真实结算链运行 5 组场景（基线 + 3 档精灵 + 1 组时间/击破/死亡变体——变体经 `fixture_variants` 采样，见 [variants-evidence](semantic-data/stage2a/) 与 `build/stage2a/score-fixtures-result.json`），每个分项、总分、等级与上表公式断言一致。基线实测：帧 3676 → 1'01/20p，击破 5/(2+1)=1 → 0p，受伤 58 → 4p，死亡 2 → 9p，精灵 0 → 15p，总分 68，RANK C，CODE NAME GUNMAN。

## A2：三组对照与惩罚来源

1. **普通基线**：结算 ELF 行 = 0/15p，TOTAL 68p，RANK C。
2. **仅改变精灵使用记录**：预置存档区使用队列 `u8[0x02037CF0+0x283]=n`（RAM 夹具；结算场景自身经 `0x080D61B8` 聚合到 +0x10，聚合后队列按其滚动规则保留痕迹 `queue283`）。实测 n=3 → ELF 12p/总分 65/RANK E(2)；n=6 → 9p/62/2；n=16 → ELF 行显示 **-1p**（显示按有符号字节渲染），内部 u8 回绕 0xFF，总字节和 (20+20+0+4+9+255) mod 256 = 52，RANK E(1)。即：**精灵惩罚字段 = 0x0202EBF0+0x10（源头为档案 +0x283/+0x284 队列），公式 15-使用数，且总分/子分均按 mod-256 字节回绕**——回绕不产生"负分变加分"的漏洞，只是把超额惩罚折回。
3. **仅切换装甲/形态**：翻转玩家档案候选装备/形态字节（+0x210..0x215 含武器槽、+0x1FD..0x1FF 基础属性区）后重跑结算，总分/等级/类别与基线完全一致（`form_flip` 断言通过）。静态侧：评分计算（0x080141FC/0x08014384）与精灵聚合（0x080D61B8/0x0801CE5C 状态1）**不读取任何装甲/形态字节**——美版 Z2 的终极/原型形态不影响评分公式本身；唯一间接路径是形态改变实际受伤量 → DAMAGE 分项。

关于"终极装甲是否改变精灵惩罚"：Z3 的 `CalcElfPenalty`（src/cyberelf.c:529）有 `menuZeroColor==MZC_ULTIMATE` 时改为惩罚 fusions 的分支；Z2 对应聚合路径（0x080D61B8 与其调用者）无该分支（静态证据，队列写入者侧见未解决问题）。

## A3：结算显示对应

真实结算画面截图（`build/stage2a/settle_baseline.png` 及 `settle_elf_{3,6,16}.png`）与内存字段逐项对应：MISSION 100%/20p（+0x07/+0x16）、CLEAR TIME 1'01/20p（+0x08/60=61s，20-⌈(61-130)负⌉=20）、ENEMY 5/0p、DAMAGE 58/4p、RETRY 2/9p、ELF n/±p（有符号显示）、TOTAL（u8 回绕和）、RANK 字母（0..6=F/E/D/C/B/A/S）、CODE NAME（BUSTER 类 → GUNMAN，称号表与 Z3 `gCodeNameSuffixs` 同构）。时间显示格式 `分'ss` 由 `0x0801D1D8` 用 `__udivsi3`/`__umodsi3`（0x080EF330）计算，证实 +0x08 为 60fps 帧数。

## A4：选定字段生命周期与一个奖励门

- 条件位域 `0x0202EBB0+4` 起的位域：位 29-38 = 实体类型 0x1D-0x26 事件（同时 EBF0+0x07 -2）；位 66-75 = 全任务 EX 条件（结算入口 `0x0801DA44`：任务字节匹配 0x08333370 表且 `rank<=4` 时置位）；结算状态4 `0x0801D6D8` 消费：匹配任务 + 位已置 → `u16[存档+0x216] |= 0x08333390[i]` 掩码 + 音效 + 结算实体 +0xC 记录；结算状态5 `0x0801D7A0` 把 7 项任务专属特殊计数（+0x24..+0x2A）转为位域置位。
- 动态验证（有界）：任务 1 不在 EX 任务表（0x08333370 = 任务 2,3,6,5,4,7,8,10,9,11），结算链全程自然执行后 `存档+0x216` 保持 0、无 EX 音效——"无门"情形验证通过。EX 门的"有门"情形需要任务 2+ 的自然通关，本轮未到达（见受阻）。跨关/读档保留：+0x216 属存档结构（`[0x02036E98]` 指针），0x0202EBB0 位域由 `0x08014104` 从存档 0x02036B7C/0x02036B9C 拷入（静态）。
