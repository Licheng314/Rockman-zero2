# 对象池、活动链遍历与延迟回收

2026-10-29。只读语义分析；既有匹配C与原ROM指令互证，不改变后台源码、构建或提取状态。

## 池头布局与不变量

06AC4(owner,tag,storage,stride,count)初始化对象池。池头固定字段为：

| 偏移 | 本轮证据支持的含义 |
|---|---|
| +0 | 对象存储区指针 |
| +4 u16 | 类型/标签参数（先按低8位处理） |
| +6 u16 | 对象步长 |
| +8 u16 | 总容量 |
| +0xA u16 | 当前空闲项计数 |
| +0xC ptr | 活动遍历游标 |
| +0x10 ptr | 单链空闲表头 |
| +0x14,+0x18 | 双向活动链哨兵的next/prev；哨兵地址owner+0x14 |

初始化使哨兵两指针都指向自己。空闲对象通过对象+0串成单链；循环按存储区步长递增，但每次压到链首，因此初始分配顺序与内存地址递增顺序相反。没有为所有对象做整块清零，不能假定未明确写的字段初始为0。

D9C38初始化的界面池标签9、对象步长0x84，给各对象+0x1C分配顺序字节，并将owner保存到全局0202F094。容量由调用者传入，本轮不硬编码某个菜单的实际对象总数。

## 分配的两种插入位置

06B84(owner)：空闲头非NULL时弹出一项，空闲计数减1，将其插到活动链的next侧（紧邻哨兵）。06B50(owner)则插到prev侧。两者都把对象+0xA半字、+0xC字和+0x10字清0，但不清整个对象，不保证动画控制块+0x6C..0x73已重置。

既有src/sub_08006B84.c已经精确匹配，其Owner.listA/listB命名可由本轮提升为“空闲链/活动哨兵next”的语义解释；本轮不修改这个C文件。

06BB8和06BF0等还有相对节点插入接口（本轮仅对06BB8读取并确认从隐式owner的空闲链弹出后插到指定节点一侧）。不能把所有创建助手都替换为同一种头插，插入位置影响遍历时机。

## 活动遍历及隐式全局owner

06B38(owner)把owner写全局0200001C，并把游标owner+0xC设置为哨兵owner+0x14。

12004(owner)随后反复：先从游标的prev移到前一个活动项，若回到哨兵就结束；否则调用item+0x14保存的回调，再读取owner游标继续prev遍历。

12034同样遍历回调，还可能在回调后依据对象标志调用099BC。1218C是另一条活动链遍历，只对对象+0xA的bit0x01置位项提交显示相关操作，不执行item+0x14的更新回调。

06C28(item)从0200001C取当前owner，解开item的活动双链，将item压回owner+0x10空闲链，空闲计数加1。06C4C(owner,item)操作相同，但owner显式传入。两者不对外部持有指针做失效通知，也不整块擦除对象。

因此06C28不是可以任意脱离更新环境调用的通用free：它依赖06B38设置正确池上下文，且不检查重复回收、item是否属于该池或NULL。跨池嵌套遍历若覆盖全局owner，需要调用者维持约束；本轮没有证明整个引擎都支持重入。

当前项被回收后，其prev仍留着原活动前驱，遍历器通过游标.prev可继续；free只覆写next去串空闲链，不清prev。这是原遍历方式的一部分，不能擅自把回收改成清零所有字段。回调若做更复杂的分配/移除，遍历行为仍须按实际链操作分析，不概括为对任意修改都安全。

## 激活动画对象退出与真正回收是两个阶段

类型3/subtype1的结束回调DBB88，以及类型2/subtype2的DB86C，都执行：

```text
item.stateWord(+0xC) = 4
item.callback(+0x14) = lifecycleTable[type][4]  // 当前两类均为06C28
item.flags(+0xA) &= 0xFE
return
```

D9CA0是类似的共用隐藏/退场标记路径。它们不立即调用06C28；设置回调后，等后续12004活动遍历再次执行这个项才移回空闲表。因此：

- 动画status3不等于已经回收。
- 清可显示位不等于已经回收。
- 写state4/回收回调也不等于这一次回调中内存已复用。
- 真正回收后内存仍在池中，可能立即被后续分配复用，外部裸指针没有代数/版本验证。

## 界面更新中已确认的顺序

外层游戏模式表的索引1为E7DB4（界面模式）。E7DB4按context[1]查0835E4F0，第1项为E7F6C。E7F6C先按context[2]分派一个控制处理器，再调用E83EC。

E83EC：04AF4准备显示链 → 12004更新0202F094指向池内的对象 → 1218C提交可见对象 → 04AA4收尾。这里控制分派先于当次对象更新、更新先于显示提交。尚未完全展开E7F6C的所有context[2]处理器，不能由这一顺序推导全部菜单路径的全局安全性。

在B组正常激活链中，E8F3C读取第一段对象进度并创建第二段对象、替换context+0x14；E8F84读取第二段结束状态，随后清context[1]并增加槽位、整理项目列表。结合延迟退场机制，控制器读取结束状态并不天然构成悬空读取。不过正常路径下每次分派的精确顺序及其它对象分配仍需逐层核对，未作运行时内存安全证明。

特别是：空闲项分配仅清部分字段，故“旧动画status仍为3”可能留在尚未初始化的复用项中。不能靠读取status3来判断任意裸指针所属对象仍是原对象；后续C封装如增加句柄验证，必须区分语义改善与原版字节匹配目标。
