# 当前开发路线：评分、三角下劈、OZ 与扩大视野

2026-11-10，按用户最新决定重订。当前只围绕以下四项工作；旧阶段 0/1/2、2A/2B/2C 的成果和证据保留作为基础，不继续追求全部旧清单、全游戏语义理解或全量 C 化。旧路线留在 Git 历史。

**验证由 Codex 自行完成**：复跑检查、核对数据和画面、修正失败、记录实际覆盖范围。没有“等待用户逐项验收”的工作门。用户只需决定尚未明确的效果和取舍；无法自证的内容标为未验证/受阻，不能当作完成。**下劈动画是明确例外：提取图片以及适配修改的前后图必须先给用户审阅，获确认后才写入改版；这不替代 Codex 自行完成技术验证。**历史“验收”指代理独立复核，不是留给用户的待办。

## 四条工作线

| 工作线 | 工作范围 | 可使用成果 |
| --- | --- | --- |
| S 评分 | 解释评分/精灵惩罚/等级/EX 关系，实施选定规则 | 规则说明、独立补丁、游戏包 |
| T 三角下劈 | 将用户所指下劈动作的细剑外观改为三角版本 | 可编辑素材、回写工具/补丁、游戏包及前后图 |
| O OZ 形态 | 研究给定 Z3 OZ 改版，在 Z2 接入玩家可操作形态 | 分阶段可玩实验包、源码/补丁、操作说明 |
| V 扩大视野 | 修改模拟器渲染/显示，首目标实际世界范围 360×240 | 独立模拟器构建、源码、配置和示例 |

S/T/O 的研究留 main；ROM 修改留独立改版分支/副本，不写回原版。V 使用单独模拟器代码库/构建，不替换已有研究核心。O/V 均包含开发，不能交一份文档就称完成。

不默认做：新增按键方案、其它敌人专项、Boss Rush、双人、ZX 全形态、其它代全武器、其它平台移植、全剧情/音效/精灵/存档格式。稳定性检查围绕四项目的实际改动及必要依赖。

## S：评分系统

已有 [2A 报告](STAGE2A-SCORE-RESEARCH.md)、[独立复核](STAGE2AB-ACCEPTANCE.md)和 [HANDOVER](HANDOVER.md)。分项/等级/显示已有局部运行证据，一个 EX 门已有混合任务 RAM 夹具的正反例。精灵使用记录与仅切换装甲须区分，不能预设独立“终极装甲扣分开关”。

1. **S1 收拢规则**：用修正后的证据整理输入字段→分项→总分→等级→EX 资格表，列出已测边界；只补阻塞修改的边界，不重跑全部长链。原 2A 超支记录保留。
2. **S2 规则开发**：优先方案是把精灵使用惩罚作为可独立配置的一项；是否仅豁免某形态、是否免除历史惩罚等尚未确定，实际实现前明确，不能擅自改成全关卡满分或直接解锁奖励。用同输入核对原版/改版的显示、总分及 EX 门。
3. **S3 游戏包**：检查规则实际影响的下一关与普通存档字段，输出补丁/游戏包及说明；不要求打通全部游戏。

S 不依赖 T/O/V 或图块消费者闭合。

## T：下劈改为三角形武器外观

[2C 报告](STAGE2C-ATTACK-CONTRACT.md)确认一个普通首斩资源的 5×224 字节布局，不能拿它当下劈资源证明。用户已明确：目标是普通空中攻击，按住下方向后保留末段向下剑光及攻击判定，不是 EX 下压技。Z3 对应 DM025 普通空中斩及 DM098 剑光的按下保持路径；仍需在 Z2 绑定实际状态和资源。

1. **T1 定位/导出**：定位下劈实际图块、拼合、调色板及帧引用，仅追其必要加载依赖。已有候选从 `0x08002548` 加载所在函数核查，不再从高地址盲扫；候选不是已证明的消费者。
2. **T2 从 Z3 提取并供审阅**：目标是直接提取 Zero 3 对应的三角形下劈动画用于替换，不默认自行重画。同时提取实际帧序列、图块、拼合与配色，先提供 Z2 原版与 Z3 提取图的同尺度对照及完整帧顺序。首批可先展示最多 4 个关键帧，但不能把预览帧数当作最终替换上限。为适配 Z2 而调整锚点、画布、调色板或拼合时，另给修改前后图，明确改了哪些内容；**用户审阅确认后才写入改版**。保持伤害框、输入和时序，除非另行授权改变。
3. **T3 版本核对与回写**：日美版共享素材是待核假设，不要求先理解全部地区差异；以所选动画的图块内容、拼合、帧序列和配色逐项比较，匹配即可复用提取结果。只在需要时解释差异，不把日版 ROM 地址照搬到美版。Z3 下劈素材调查不因缺未修改美版 OZ 差分基线而整体停止；来源 ROM/源码提交、素材索引与变换记录须保存。审阅通过后适配 Z2 的资源格式和帧引用。
4. **T4 游戏包**：Codex 检查左右朝向、完整动画周期、配色与共用资源反例，保留前后图、可编辑资源和恢复方法；输出补丁/游戏包。

若只改图块即可实现，不强求先理解全部图形格式。

## O：参考 Z3 OZ 改版，在 Z2 加入可操作 OZ

### 已识别材料

- 用户给定 `Mega Man Zero 3 (USA-oz).gba`：16MiB，header `MEGAMANZERO3 / BZ3E / revision 0`，SHA1 `f1835aaceadebe08bd4d6178947418d3e077a667`。已完成从开机至普通操作的有限复跑并定位扩展玩家更新入口，尚未取得特殊动作触发或完整机制，见[参考记录](semantic-data/oz-reference-20261110.json)。
- 本地 [RMZ3](https://github.com/mmzret/rmz3) 固定提交 `2a28700e0a74edd9578737c3b3435ced9d074045`，对应日版。**美版 OZ 与日版源码不可按地址直映，全部差异也不能算作 OZ 补丁。** 附近两份其它 Z3 分别为日版另一改版、欧版标识，不是可信同版美版基线。
- 参考 `src/player/zero/`、`src/boss/omega_zero.c`、`src/projectile/omega_zero.c`、`sprites/dynamic/omega_zero/` 与相应剑资源。Boss AI 不能直接当玩家回调；`NON_MATCH/MODERN` 实现只作线索，不是精确编译证明。

### 分批研究与开发

1. **O1 参考改版取证**：从开机记录进入 OZ 的方式、按键、招式、切换、受击/落地表现；核对同地区/修订未修改美版 Z3 的基线来源。缺基线仍可记录行为和定位日版源码语义锚点，但不发布“精确 OZ 补丁差分”结论，不下载 ROM 补基线。
2. **O2 改动机制**：基线齐备后生成代码/数据/跳转指针/扩展区差异索引；只绑定一条玩家输入→OZ 动作→攻击对象→清理样本。确认是改玩家、借 Boss 对象还是新控制器，再选 Z2 接入方案，不先普查全部招式。
3. **O3 Z2 最小可玩包**：可进入/退出 OZ、基础移动和一招经 O1/O2 确认的代表攻击；协调玩家状态、所有者、碰撞阵营、资源和中断清理。仅换颜色不算 OZ；首包也不宣称参考改版全招式完成。
4. **O4 逐招扩充/稳定**：以参考 ROM 可复现的招式清单每批加入一招；检查实际扣血、重复生成/清理、切形态、受击、死亡/重开及普通存档边界。每包附功能清单、源码、补丁、可启动游戏包和限制。

O3 复用 T 的必要图形知识与既有 2B/2C，不等待旧清单全部完成。跨代代码、对象布局和地址不照搬。参考 ROM 只读保留，不提交原 ROM 或大段提取素材；开发成果保留来源和修改记录。

## V：修改模拟器扩大视野

首目标是 **360×240 的世界范围、保持像素比例**；原 240×160 可放中央，左右各扩 60、上下各扩 40。允许外围缺图/缺对象，须如实显示/标注。拉伸、黑边、地图循环重复、历史残影不能算看到真实外围。

优先评估 [mGBA 软件渲染器](https://github.com/mgba-emu/mgba/blob/master/src/gba/renderers/video-software.c)和[视频接口](https://github.com/mgba-emu/mgba/blob/master/include/mgba/internal/gba/video.h)。ROM 位于 VBA 目录不代表必须改 VBA。实现前固定模拟器提交、许可证和构建环境；独立实验显示路径复用原 PPU 状态/资源，不替换研究核心。

1. **V1 可见性探针**：普通关卡固定场景，检查 VRAM tilemap/OAM 已有多少中央画面外的数据，记录滚动、裁剪和地图流式加载限制；最多补一处滚动边界。输出外围可绘制/缺失区域图。
2. **V2 扩展渲染原型**：修改前端输出尺寸、帧缓存和边界绘制，首期只支持样本实际模式。中央保留原 240×160 标准渲染，外围为实验层；不能简单将 GBA 扫描线、VBlank/IRQ 或游戏节拍改成 240 行。记录窗口、对象坐标回绕、优先级和逐扫描线效果限制。
3. **V3 可运行实验包**：交付模拟器、360×240 开关/配置和截图，关闭后回标准画面。Codex 比较同输入下中央像素与游戏状态，检查只读扩展显示不改变物理、伤害、输入或时序，不能反写模拟状态。
4. **V4 按证据补强**：若游戏未加载外围图块或已裁掉对象，模拟器本身无法凭空补齐。先交付标明缺失的残缺视野；之后再评估 Z2 专用地图解读/额外可见对象采集。ROM 配合改动另记，不直接扩大敌人生成和 AI，不宣称适用所有 GBA 游戏。

V1/V2 可独立于其它线开展。原版与 OZ/Air Actions 兼容性分别记录。纯 ROM 在普通模拟器上仍为 240×160；扩视野成果必须包含模拟器，不能只发一个 GBA 文件就称完成。

## 执行顺序与自动收尾

先做 S1、T1；尽早用 O1 明确参考改版/基线条件，用 V1 判断外围数据是否可用。随后 S2/T2 形成小成果，O2→O3、V2→V3 分别推进。本次只重订计划与识别文件，没有启动研究进程、改 ROM 或编译模拟器。

- 每次派工一份有限小包：默认最多 90 分钟，70 分钟后不做新实验；最多 3 轮明确假设。研究包首次新增深入函数至多 3 个，必要依赖计数；扩展另划下一包，旧超支不抹掉。
- 模拟器/素材开发以一个可运行里程碑分包，不靠函数数衡量。每包说明输入、成果、自行执行的检查和阻塞，不以 Token 消耗为目标。
- Codex 自行复跑关键样本，核对截图/帧序列和实际字段。区分静态、RAM 夹具与自然流程；没运行的功能不记为游戏内通过，自称通过不替代复核。
- 原版门禁仍须精确重建；改版单独记变更范围、产物散列与回归。阶段开发包含游戏包，不默认发布新 Release。
- 首个执行包先检查工具/解释器/模拟核心。原系统 Python 路径仍失效，但已找到内置 Python 3.12.14 并成功运行 Pillow 和文档检查；capstone 未安装，尚未复跑模拟器。按实际包补最小依赖，不把依赖缺失当游戏逻辑结论。
- 每包结束自动整理状态、短交接与小证据，受阻保存续跑点；没有新授权任务就停止，不设置循环，不等用户逐项验收。
