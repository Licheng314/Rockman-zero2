# 有限语义解读路线：以可修改成果验收

2026-11-01 建立，2026-11-08 按玩家反馈修订研究优先级。目标是支持主人公能力/属性、评分规则、操作手感及有限攻击模组的理解与后续修改，保留贴图/画面研究，不追求全游戏语义解读。背景见[游戏信息](GAME-CONTEXT.md)，已有研究入口见[研究目录](semantic-modules.md)。

本次只修订语义研究目标，不实施玩家提出的改版功能。阶段 0、1、2 的既有验收不变；新增阶段 2A → 2B → 2C 后，再考虑尚未启动的阶段 3。先形成可验证的原版行为解释，再另行确定改版方案。

以下是工作边界与建议验收标准，尚未完成的内容不得因写入路线就算完成。函数数是每阶段新增深入研究的上限，不是声称全系统只有这些函数。已有报告可复用，只有通过所需验证才计入阶段成果。

## 阶段0：汇编提取收尾，独立于语义路线

- 阶段 0 已验收。固定范围内正式地址覆盖 100%，地址空洞、待查原始标记及已知的常量与指令冲突均为 0。详见[阶段0现状](ASSEMBLY-CLOSEOUT.md)，不能将地址覆盖当作指令或功能理解进度。
- 目标：对预定代码区剩余范围逐一分类，继续提取有证据的代码；有界失败留明确原因。
- 验收：每个未覆盖区间有归属，区分代码、池字/表、填充、头部和待确认；可确认代码进入正式构建，全ROM精确验证。
- 100%只能指明确定义的分类或覆盖指标。若数据/头部使原“纯代码覆盖”分母不准确，须公布原口径和分类口径，不移动分母掩盖未完成，不把原始字节包一层就宣称全部指令已反汇编。
- 分类账、完整 ROM 与逐段终点校验已通过。下一阶段以主人公基础参数的可修改成果单独验收。

## 阶段1：主人公基础修改，第一优先

**目标：可以可靠修改并验证少量主人公基础参数。**

范围只含：

1. 主人公实例的定位、关键字段及读写者。
2. 按键→动作状态的最短入口链。
3. 地面移动、跳跃、冲刺的关键参数及生效条件。
4. 当前/最大生命、受到伤害、无敌时段及一次回血的关键路径。

固定为普通难度、一个常规地面测试场景、固定形态与装备。只追踪阻塞上述修改的基础依赖；不全解地形引擎、全部受击类型或每个动作。

**工作上限：新增深入研究最多20个函数，最多2个测试场景，最多4个示范修改。** 优先选择移动速度、跳跃初速度、生命上限、无敌时间；若某项不由简单参数控制，记录原因并选择本范围内可验收项，不硬称“改一个数即可”。

**交付与停止：**

- 一份主人公字段/参数表，写地址、宽度、单位/定点格式、有效条件、读写入口及持久性。
- 至少2个不同参数的实际修改实例，在模拟器中展示改前/改后；恢复原值后行为复原。
- 原版构建仍需精确匹配；改版ROM预期哈希不同，单独验证改动范围及运行行为，不把改版送进原版SHA1门禁。
- 达到目标立即停在本阶段边界；不顺带扩大为完整玩家状态机或全部C还原。

## 阶段2：四武器与能力配置

**目标：能够调整常见攻击/成长配置，而不必解完全部敌人。**

范围只含：

- 剑、枪、盾、锁链：每种各选1种普通攻击和1种可用蓄力/特殊攻击，定位输入、攻击生成、伤害/碰撞描述符及关键时序。
- 属性芯片：选择和生效路径；用1个可重复受击目标验证适用攻击及至少一组属性差异，不普查全部Boss抗性。
- EX：每武器至多选择1项，定位使能位、触发条件和分派；取得条件只追到实际门控，不重写整个评分系统。
- 电子精灵/回血罐：各选1种与生命相关效果；定位使用、数量或效果字段。存档仅跟踪选中字段是否保存。

**工作上限：新增深入研究最多40个函数；4武器×2种攻击、最多4个EX样本、1类芯片对照、2种恢复样本。** 已有基本路径复用，不穷举所有形态、等级、难度、技能组合。组合输入与连段只解释所选攻击需要的分支。

**交付与停止：** 形成配置位/参数/描述符表，武器样本逐项有原ROM依据；至少完成一个攻击参数改动、一个能力使能改动、一个恢复参数改动的实际验证。只定位未实测的项明确标记；表内样本之外不称“全武器系统完成”。

## 阶段2A：评分规则与能力使用的关系

**目标：解释一个关卡的分项计分、汇总与评定，以及终极装甲/精灵记录是否、何时影响这些结果。不是先取消扣分。**

- 复用[伤害评分累计研究](semantic-hit-consumers.md)，核对伤害记录、实际损血和结算扣分的差异；已有静态证据不自动算运行验收。
- 定位选定关卡各评分项的输入字段、重置/累计/结算时机、上限和舍入规则，以及总分到等级的映射。只跟踪该样本实际经过的规则，不普查全部关卡专用阈值。
- 把“拥有装甲、当前装备、精灵已使用记录、当前效果”分开，先确认评论所述惩罚是否存在及其触发条件。至少比较普通装甲对照、仅切换终极装甲、精灵使用记录对照；控制时间、受伤等其他输入，不能把相关变化当因果。
- 区分当关影响与跨关/读档保留；仅跟踪所选惩罚字段的生命周期。EX 取得只衔接到阶段 2 已定位的资格门，不扩大为全部奖励脚本。

**工作上限：新增深入研究最多10个函数、1个关卡结算场景、上述3组对照。** 首批至多5个函数，先确认惩罚来源，再决定是否有必要追踪其他评分依赖。

**交付与停止：** 一张分项→总分→等级→选定奖励门的数据流表，附字段/公式/读写者与可复跑结算样本；比较程序内结果和结算画面。运行夹具只覆盖结算子程序时必须注明，不能称完整通关验证。若假定惩罚不存在，应给出对照证据，不为满足需求强行找一个“扣分开关”。

## 阶段2B：动作衔接、输入窗口与实际连击

**目标：对有限招式链解释“输入是否被接受、动作能否切换、后续攻击是否真正扣血”三件事，为手感改版提供依据。不是整体复刻 Z3。**

- 选普通剑三连斩、蓄力斩、升龙及下戳作为核心样本；普通枪弹只作为一条混合连招的前置，不扩成全武器连段表。先核对对应 Z2 招式和使能条件是否存在。
- 记录按住/新按/松开、输入缓冲或取消窗口、动画事件、攻击生成和清理时机；明确冲刺、受击、落地、碰顶等状态转换中谁写速度、重力和动作字段。无输入缓冲的实测结果同样有效，不预设原版具备某机制。
- 对升龙分别观察短按与长按的速度、位移、阶段与退出原因，区分招式自身轨迹和通用跳跃处理。不先假定评论中的两代差异完全准确。
- 分开调查招式切换规则与目标受击规则：攻击等级/优先关系、保护计数、同次攻击重复命中、属性与命中停顿。禁止用“动画接上”证明连击成立，也不用全局关闭无敌来证明原版机制。
- 最多3条输入序列：三连斩→升龙、蓄力斩→三连斩、枪弹→蓄力斩→三连斩→升龙→下戳。它们是待验证假设，允许得出中途不接受输入或不扣血的结果。

**工作上限：新增深入研究最多20个函数、上述3条序列、最多2类目标（普通敌人与一名可重复测试的 Boss）、最多2个测试场景。** 如需第三个位置样本检查碰顶，必须替换既有测试场景或另行提出扩展，不顺带扫描全部地形。

**交付与停止：** 一张有限动作转换表、一份按更新次数记录的输入/动画/攻击对象/速度/实际 HP 时序，以及成功/失败连击对照。Boss 样本未取得时明确未完成的验证，不用普通敌人结果外推。给出每项手感诉求属于输入、状态转换、运动还是命中规则的结论及未决依赖，不交付功能补丁。

## 阶段2C：有限角色攻击模组的接入条件

**目标：解释替换或新增一招需要哪些原版接口和资源，形成可供开发者使用的接入说明。不是直接制作 OZ 角色或通用模组框架。**

- 复用 2B 的剑样本，追完整生命周期：输入门→角色动作→动画事件→攻击实体→碰撞/伤害→退出与销毁。最多选一招近身攻击及一个已有投射物样本，列明生成失败与中断时的行为。
- 分清角色本体、武器对象及特效对象的职责，记录所有者指针、对象池/类型表、生成参数、对象上限及清理约定。不能仅凭类型字节命名对象。
- 列出模组所需的字段和约束：动作入口、使能位、速度/重力写入者、命中参数、动画/图块/调色板/音效引用、存档是否涉及。未知处明确保留，不凭未使用外观推断可安全复用的 RAM 或 ROM 空间。
- 如使用 OZ 作为案例，先绑定具体招式演示及预期行为；未指定则只研究现有招式。敌方招式由 AI 驱动，不能直接当作玩家动作回调使用；跨游戏资源和代码也不能按地址照搬。
- 只登记资源加载与容量依赖，图像编辑和回写仍归阶段 3，不提前展开全部角色素材。

**工作上限：新增深入研究最多15个函数、1个近身攻击、1个已有投射物、1份接入说明。** 若闭合依赖超限，交付已知接口与阻塞，另行讨论是否扩展；不自动实现新角色、招式全集、可配置加载器或双人模式。

**交付与停止：** 以可读伪代码、字段表、对象生命周期和调用关系描述样本，标明稳定入口、尚未证明的假设及所需验证。后续作者能据此定位各环节和估计缺口；不以新增 C 函数数量或报告篇幅作为验收指标。

## Z3 对照方法：贯穿2A、2B、2C

参考 [RMZ3 工程](https://github.com/mmzret/rmz3)，重点入口为 [Zero 地面攻击](https://github.com/mmzret/rmz3/blob/main/src/player/zero/attack/ground/idle.c)、[空中攻击](https://github.com/mmzret/rmz3/blob/main/src/player/zero/attack/air.c)、[剑攻击实体](https://github.com/mmzret/rmz3/blob/main/src/weapon/saber.c)及[碰撞结构](https://github.com/mmzret/rmz3/blob/main/include/collision.h)。评分规则按需要查找对应实现，不能因为两代有相似字段就假定规则相同。

1. 每批记录 Z3 仓库提交、文件和符号；区分已匹配实现、`NON_MATCH`/`MODERN` 解释代码与仍引用的汇编。Z3 源码名称提供线索，不直接作为 Z2 字段的证明。
2. 从一个具体问题出发，先提取 Z3 的字段读写、状态条件和调用关系，再按常量、表形状、调用邻域与运行轨迹在 Z2 寻找候选；不使用固定地址差或结构体偏移机械映射。
3. 每个问题记录“Z3 行为/证据 → Z2 候选 → Z2 验证 → 相同/不同/未定”。日本版 Z3 与美版 Z2 的版本差异始终保留。
4. Z3 运行比较仅在对应 ROM 与可复跑环境具备时执行；只有源码时标成静态对照。Z2 结论仍须由 Z2 汇编或原版运行支持，状态切换、伤害与计时结论优先做运行对照。
5. 优先复用已有 Z2 研究和改版暴露的问题。改版分支、测试插桩和人工写内存结果都不能冒充原版自然行为；不把已发布改版的速度/重力处理回填成原版定义。

## 阶段3：贴图及局部画面修改（暂后排）

**目标：把一项可辨识的主人公视觉资源完成导出→编辑→回写→游戏内确认。**

范围只含主人公一个明确动作，最多4个连续帧及其实际使用的调色板。另可选择1个该动作特效作为附加样本。需要时定位帧头、图块/压缩数据、OAM拼合、调色板、加载缓存和容量约束。

**工作上限：新增深入研究最多20个函数，1个动作、4帧、1个可选特效。** 首次选容易独立替换的样本；不做全图鉴、不扫描全部关卡资源、不承诺整体性能或帧率优化。

**交付与停止：**

- 可辨识的原始拼合图、可编辑导出物及资源位置/格式/大小限制。
- 一次像素或配色编辑成功回写，在真实游戏流程中显示，保留截图或可复现操作。
- 邻近图块、动画切换和配色不受非预期影响，能恢复原版。
- 画面优化仅验收一种有明确样例的局部改进；没有样例就不额外开“全局优化”任务。

## 后续按需阶段：不默认展开

阶段 2A 已包含有限评分/奖励门研究。超出该边界的其他评分规则，以及选中字段的存档/读档、难度差异、某一关事件或其他 Boss，只有具体需求确实依赖时才开单独小包。每包先给最多10个新增深入函数及一个可复现问题；超过上限时写出阻塞与可选方案，不自动扩成全系统。

默认不做：全部关卡流程、全部Boss/杂兵AI、全部NPC/CG/剧情脚本、全声音系统、全部精灵、完整存档格式、全功能C化。

## 每个阶段统一的控制规则

- 每个阶段按小批次执行：首次最多5个新增深入函数；已有范围不明时先盘点，不直接消耗整阶段上限。
- 阶段 2A/2B/2C 的上限独立计账，复用函数不重复计数。依赖追踪也计入当前阶段上限；达到上限就停，不能以“还在准备”为由绕过边界。
- 新增阶段先交原版行为解释和复跑证据。受控改值/调用夹具只作为因果验证手段单独标注，不默认生成、提交或发布新的改版 ROM；实际改版目标另行确定。
- 参数修改示范不要求整条调用链先还原成C；需要复杂行为修改时再按需做C，精确匹配成功才集成。
- 单点最多3轮明确假设验证；仍无进展即记下入口、已有证据、失败原因和下一步，换本阶段其他任务，避免长时间空转。
- 阶段上限耗尽而未达到验收：标“未完成/受阻”，交付可复用证据；不得通过减少验收项或把静态检查冒充实测来宣告完成。
- 不因偶然遇到有趣函数扩大范围。只收一条线索入待办，不另开长报告。
- 原ROM执行、模型、静态推断和游戏内实测分别记录；攻略只提供术语与验证场景。
- 每阶段结束记录已验收项/目标项，报告“本阶段完成度”；不把几个样本的完成率叫作全游戏完成率。
